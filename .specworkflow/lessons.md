# このプロジェクトで確認したこと

- Call to the Pastのマスターは原案の監禁脱出、道具のない薄暗い空間、身近な実物写真を保持する。抽選を作りやすいという理由で設備修理ゲームへ置き換えない。
- Codex native imagegenはこの環境でoutput_hintにローカル保存先を返した。モデル指定引数はなく、Flare指定済みとは報告できない。パスなし写真添付は同じ原本のローカル保存を依頼する境界が必要。
- 状態確定、画像の作成/修正、動画の承認/送信は別段階にする。メディア失敗・文章代替でゲーム回数を二重消費せず、代替を実生成合格に数えない。
- unittestを検証コマンドにするなら関数形式テストもdiscoverで実際に検出されることを確かめる。単にコマンドが動くこととテスト実行件数を区別する。
- 単体配布するスキルが終了処理に必須の兄弟スキルへ依存すると、受け手のインストール差で終盤だけ失敗する。必須ランタイムは同梱し、孤立コピーからの実行と配布ZIP・インストール先のハッシュ一致を検証する。
- **目標表示を直す前に、現在使う設定と表示経路を確認する**: 標準例 `mobile-playtest.json` だけを直したため、既定の `story-catalog.json` では障害名が「現在の目標」に残った。`DEFAULT_SCENARIO_PATH` → カタログ変換 → 公開状態 → UIを確認し、全構成・全言語を検証する。障害の名前と、対象・達成状態を動詞で示す `objective` を分け、内部の詳しい解法を目標欄へ出さない。
- **生成失敗の修正は、実シナリオの入力と実AIの検査を分けて確認する**: エンディングの模擬テストは成功したが、未登場factsと物理描写の欠落を見逃し、再試遊で失敗を繰り返した。本編・結末間の公開範囲とvisualDescriptionを照合し、実際のstory-catalogで回帰検証する。実APIのコード・判定・時間・トークン消費を調べ、未取得なら直接原因・解消とも未確定と明記する。検証の上限と外部送信を具体化し、必要な承認は早めに取得する。
- **断続的なテスト失敗を再実行の成功だけで片付けない**: 画像取得のHTTP 400を再実行で通ったとして残したが、保存前にreadyを通知する競合だった。非同期の保存をテストで保留して必ず再現させ、完成状態と利用可能な画像IDを同時に公開することを検証する。
- **所持品リストを室内に存在する物の一覧として扱わない**: 実APIのエンディング検査が、初期画像からある背景の端末と箱を「所持品が空なのに追加された道具」として拒否した。生成・演出・検査すべてでプレイヤーの道具と既存の背景を区別する。修正確認では拒否された同じ画像を再検査し、さらに解除済み状態と未解除の画像の組み合わせを拒否する対照試験を行う。検査を緩めただけの見かけの成功と区別する。
