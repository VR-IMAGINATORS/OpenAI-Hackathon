## 取り入れたい意図

今回の評価から、**自分が出したアイテムが次々に登場し、その使い方や結果がつながって一本の動画になること**を、優先すべき体験と解釈する。これはユーザーの理由を確認済みとする断定ではなく、実装方針の提案である。

「結末に必要な道具を1つ選び、残りを省く」という順序を変え、**まず全アイテムの見せ場を組み、動作の長さや編集を調整して成立させる**。多少忙しい映像でも、プレイの工夫が多く見える案を比較の第一候補にする。人物や道具を削るだけで自然さを改善したことにしない。

前回のWeb修正 `1bfd073` は直近2行動の接続とカット明示まで。序盤のアイテムを候補へ戻す変更ではなく、この意図を十分には満たしていない。

## Webへ取り入れる具体案（未実装）

### 1. 全プレイのアイテムと、実際の使い方を対応づける

- 終了時の在庫だけでなく、全確定行動の `items`・`usage`・前後状態・成否からアイテムごとの履歴を作る。消費・破損した道具や失敗した工夫も対象にする。
- そのプレイで具現化された各アイテムに、原則1回は見せ場を割り当てる。使った道具はその実行と結果を優先する。合成・共同使用なら一つのショットで複数を見せる。用途を変えて何度も試した場合も、同じ道具の繰り返しで尺を占めないよう圧縮する。
- 具現化したが使っていない物は、実際に存在した姿として登場させる。新しい突破能力を与えたり、失敗した道具を成功させたりはしない。猫などが登場していた場合も、履歴にある役割・状態で映す。

### 2. 全アイテム案を先に作り、省略より編集を先に試す

- 基本構成は「アイテムAの工夫と結果→B→C→確定した結末」。実行済みの過去の出来事を時系列で映画化する。
- 物を手に取るまでの時間、移動、同じ操作の繰り返しを短くする。各アイテムの識別・接触・変化が読める短いカットでつなぐ。
- 道具の変形や瞬間移動でつなぐことを避け、持ち替えは明示的な編集で省く。消耗品は使われた当時の状態で描き、最後に新品へ戻さない。
- `itemId / actionId / shot / depiction` の短い対応表を同じ演出要求内で出力させる。サーバーでID・成否・時系列と全アイテムの記載有無を検証し、黙って最後の1件だけを採用した出力を見つける。自動検証で「実動画にも映った」とは判定しない。
- 尺や根拠が足りない場合は、対象アイテムと具体的な理由を残す。結果の痕跡だけになった場合も「使用場面を映した」と数えない。アイテムを多く出す方針のために課金回数を自動増加させない。

### 3. データ側の直近2件制限も変更する

| 現在の箇所 | 必要な変更 |
| --- | --- |
| `apps/local-server/ending-ai.ts` の `usedActionIds.max(2)`、`slice(-2)`、ID検証 | 全確定履歴から映像対象を選べる範囲へ改訂。アイテム対応表を検証できる出力契約を作る |
| 同ファイルの成功・直近優先 | 全アイテムの登場・使用場面のカバーを第一候補にする。成功順だけで失敗した工夫を落とさない |
| `apps/server/ending-jobs.ts` の行動前参照収集 | 最新2件だけでなく、映像候補の全履歴から終了時点で完成済みの参照を選べるようにする |
| `apps/local-server/hosted-runtime.ts` と `ending.ts` の `recentActionScenes` | 実際の参照選択は現在EndingJobsが所有する。packet側にも直近2件の重複表現があるので、変更時は意味をそろえる |

`EndingPacket.actions` と演出入力には既に全行動がある。履歴の収集から作り直す必要はない。一方、promptだけで「全アイテムを使う」と追記しても、序盤の行動IDをサーバーが拒否するため不十分。

画像参照は完成済み素材を使い、追加待機や新規の中間画像生成は基本案へ含めない。ただし、2枚の添付画像だけでは全アイテムの見た目を伝えきれない場合がある。画像根拠の不足と演出上の省略は別の問題として記録する。画像不足時に事実のない再演を許す変更にはしない。

### 4. 当時のNormalを使った構成比較

以下は文書に残る確定履歴を使った**新しい脚本案**であり、当時の良かった動画を復元したものではない。

| 時間の目安 | 新しい案 |
| --- | --- |
| 0〜3.5秒 | マジックハンドが目隠しへ作用し、外れる。最初の工夫を実際の動作で見せる |

## 待ち時間・リスクと次の検証

第一案は、演出1要求・開始と終了の2画像・15秒動画1本という工程を維持する。追加の固定待機は0にできるが、対象履歴・対応表・動作が増えるため、実際の出力時間と画像再試行率は変わる。**この拡張が追加7秒以内に収まるかは未検証**。前回の直近2行動のprompt修正に対する見込みをそのまま流用しない。

デメリットは、15秒内の各動作が短くなること、道具の取り違えや持ち替えの破綻が増えること、アイテムが非常に多い場合は全使用場面を読み取れる尺が足りないこと。同じモデル・尺・解像度でも、文章量や画像再試行に応じて費用は変わる。

実装する場合は同じ履歴・素材・生成条件で、現行版と「全アイテムから組む版」を比較する。見るべき点は、プレイヤーが出した物と使い方を何個認識できたか、攻略の積み重ねが伝わるか、どちらの映像をユーザーが好むか、追加所要時間。自然さだけを合格条件にして、工夫を省く方向へ戻らない。

今回はコード変更・実API生成・全体テストの再実行は行っていない。履歴と現在のデータ経路の読取調査、文書の出典照合を行った。
