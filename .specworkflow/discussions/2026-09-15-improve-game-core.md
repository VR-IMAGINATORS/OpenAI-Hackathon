# 2026-09-15: 調査・推理を中心にするシナリオ拡充と評価

## 背景

写真の自律使用でテンポは改善したが、必要な道具を送り続けるだけの体験に寄った。電話越しの相棒に観察を頼み、情報からユーザーが突破口を推理するゲームへ進める。proposal/improve-game-core/improve-game-core.mdに対してgrill-meを行い、Q26で合意内容を確定した。

## 判断と理由

| 質問 | 決定 | 理由・退けた案との比較 |
| --- | --- | --- |
| Q1 | 調査を攻略の中心にする | 背景を任意追加するだけでは道具送り中心の体験が変わらない。会話回数の強制はしない |
| Q2 | 舞台・障害・元の解法を維持 | 完全オリジナルや新しい必須条件を避け、確認負担を抑える |
| Q3〜4 | 標準は観察のみ。仮説、道具提案までの3段階を設定 | 会話の豊かさとユーザーの推理の余地を分けて調整 |
| Q5 | 概要から対象の細部へ | 特定の言い方を当てさせず、調査する入口を示す |
| Q6 | 無害な細部だけ補完、攻略情報は固定 | 想定外の質問への自然さと解法の一貫性を両立 |
| Q7 | 完成構成単位で拡充・保存 | 個別断片を後で組み合わせる矛盾を避ける |
| Q8 | 人間がレポートを見て採用 | 今回は事前生成。自動採用せず、体験の確認材料を渡す |
| Q9〜10 | 会話での到達性と面白さを評価。面白さは改善提案まで | 将来の無人評価に向けて根拠を蓄積。好みの点数で自動修正しない |
| Q11 | 実ゲームと共通ハーネスでテキスト検証 | ツール内専用進行役だけの成功を避ける。実音声は別検証 |
| Q12 | 正解の印のない共通日用品一覧 | 道具選択を比較可能にし、写真認識は今回の模擬検証から除外 |
| Q13 | 丁寧な調査、大ざっぱな質問、早めの道具試行 | 一つの理想的な攻略だけに偏らせない |
| Q14 | プレイヤーと評価者の両方を複数モデル化 | 既存の独立評価方針に従い、評価者の意見の違いも残す |
| Q15〜16 | 基本9プレイ。最初は3プレイで費用計測し残りを判断 | 全組み合わせで比較可能性を確保しつつ、初回の費用不確実性を抑える |
| Q17 | 検証役が具体的不備を確認した場合だけ修正 | 未クリアや早いクリアを機械的に不合格にしない |
| Q18 | 修正版は別の版で3プレイから再検証 | 旧版の成功を新しい設定の保証に使わない |
| Q19 | 設定不備だけ自動修正。実装不具合と不明は報告 | シナリオの説明追加でハーネスの不具合を隠さない |
| Q20 | 補完はプレイ内限定 | 確認済み完成シナリオをプレイによって勝手に変えない |
| Q21 | 初期画像のみ初期公開情報へ整合。調査画像は追加しない | 対話に集中し、生成待ちと費用を抑える |
| Q22 | 実プレイでは調査・相談中も時計を進める | 緊張感を維持。既存停止条件は維持し、総時間を実機調整 |
| Q23 | 模擬は最大25ターンを初期値に設定可能 | API速度を推理力と混同しない。未クリアと検証未完了を分離 |
| Q24 | 評価ごとの積極性を固定、今回は観察のみ | 暗黙の27プレイ化と比較条件の混在を避ける |
| Q25 | 初回は既存完成構成1件 | 費用と一連の運用を先に確かめる |
| Q26と追記 | 仕様化を承認。元ストーリーを含むレポートを提出 | 元の全文、拡充後、差分、元ギミックと解法の維持を把握したいという要望 |

## 費用に関する合意

提示した7〜20 USD/1件は拡充＋9プレイ＋複数評価の未実測概算。15〜25往復、テキストのみ、大きな修正反復なしを仮定した。150円/USDは換算例。支出上限や実行承認と同一視しない。初回3プレイを計測し、残り6プレイを実行する判断を待つ。

参照した既存設定はconfig/auto-mission/default.json。生成・検証Astra、独立評価Sol/Luna/Terra。今後も各役割・モデル・条件・使用量を明示する。既存measurement.mdの約1.07 USDは旧生成ツールの単発実績であり、新しい模擬プレイループの実測ではない。

## 影響範囲と反映先

仕様: specs/improve-game-core/spec.md。今後の計画対象はtools/auto-mission、config/auto-mission、シナリオデータ、共有スキーマ、apps/local-serverの知識・会話・状態管理、実ゲームへの採用経路、比較HTML、回帰テスト。既存のオリジナル生成モードを維持する。

## 後続の設計事項

初回構成、データ形式、採用・再開の操作、モデル別割当、費用と再試行の上限、HTML比較レイアウトは計画段階で具体化する。今回コード実装、課金API実行、GitHub起票、マルチレビューは行っていない。製品内の複数AI評価は、開発時マルチレビューの省略と矛盾しない。

## 再評価する条件

3プレイ実測で費用・会話長が想定を大きく超える場合は実行構成を見直す。人間の感想と面白さ評価の乖離が大きい場合は、無人採用へ進む前に評価基準を修正する。元の解法を維持するだけでは調査に意味が生まれない場合は、追加必須条件を黙って入れず改めて方針を相談する。
