1. App Serverはどこにいるのか

App Serverは、自分で起動するCodexのプロセスです。OpenAIが提供するモデル推論サービスとは別の層にあります。あなたのプログラムはApp Serverに要求を送り、App Serverが認証とエージェントの実行を担当して上流と通信します。画面はReactでもTUIでも構いません。

React／スマホ→ HTTPS →ゲームサーバー→ stdio →Codex App Server→OpenAI推論
層責務この案で持たせないもの
ブラウザ撮影・音声・操作・ログイン案内Codexの資格情報、任意RPCの実行権限
ゲームサーバープレイ所有者・正本状態・予算・結果検証モデルの文章だけで状態を無条件更新する処理
自作Codexアダプタープロセス・RPC・イベント・型変換・中断独自のゲームルール
App ServerCodexの認証、会話、推論とツール実行の調停ゲームの唯一の正本状態

GPT-Liveは別経路で残します。現行の音声から届く委譲をゲームサーバーが受け、Codexの判断を検証した後に事実を音声側へ戻す設計です。音声ソケットをApp Serverへ丸ごと差し替える例ではありません。

混同しやすい4つのID

ID用途例
playIdゲームの1プレイ誰のゲーム状態を変えるか
requestIdゲーム操作の重複排除撮影送信の二重処理を防ぐ
RPC id通信の要求と応答の対応id=17への応答をPromiseへ戻す
threadId／turnIdCodexの会話／その1回の実行どの実行の通知かを識別する

threadは会話の入れ物、turnは1回の依頼と処理、itemはその中のメッセージやツール実行です。RPC idを同じ値で再送しても、ゲーム処理の冪等性が得られるとは考えません。

2. 通信の基本：HTTPの1往復とは違う

最初のPoCは子プロセスのstdioを使います。1行のJSONが1メッセージです。要求にはidがあり、応答はそのidを返します。通知にはidがありません。さらに、App Serverからクライアントへの要求もあるため、受信したid付きメッセージをすべて応答とみなしてはいけません。公式プロトコルはJSON-RPC風ですが、ワイヤー上にjsonrpcヘッダーを付けません。通信の公式仕様

ゲーム側 → { id: 1, method: "initialize", params: { clientInfo: ... } }
Codex   → { id: 1, result: ... }
ゲーム側 → { method: "initialized", params: {} }

ゲーム側 → { id: 2, method: "thread/start", params: { model: selectedModel } }
Codex   → { id: 2, result: { thread: { id: "thr_A", ... } } }

ゲーム側 → { id: 3, method: "turn/start", params: { threadId: "thr_A", ... } }
Codex   → { id: 3, result: { turn: { id: "turn_B", status: "inProgress", ... } } }
Codex   → { method: "item/completed", params: { threadId: "thr_A", turnId: "turn_B", item: ... } }
Codex   → { method: "turn/completed", params: { threadId: "thr_A", turn: { id: "turn_B", status: "completed", ... } } }

// 読みやすさのための概略。実際は各JSONを1行で送る。
// 通知と応答の到着順をこの図どおりと仮定しない。
最重要：await rpc.call('turn/start', ...)で得られるのは実行の受付です。判断が終わったかは通知を追って確定します。完了通知も「JSONが正しい」「ゲームに適用してよい」まで保証しません。

3. 自作する最小RPCクライアント

下記のpendingは「RPC応答待ち」、journalは「実行通知待ち」です。別々に管理します。型は導入時に固定したCodexバージョンから生成し、コード例のany相当の扱いを置き換えます。

// 開発時だけ実行するコマンド。今回の作業では実行していない。
codex --version
codex app-server generate-ts --out ./generated/codex

// 以下はTypeScript風の設計例。補助関数は後述の契約で自作する。
const child = spawn(resolvedCodexExecutable, ['app-server'], {
  cwd: isolatedWorkDir,
  env: buildAllowedEnv({ CODEX_HOME: isolatedCodexHome }),
  stdio: ['pipe', 'pipe', 'pipe'],
  windowsHide: true,
});
// buildAllowedEnvは必要なPATH・OS/CA設定だけを許可する。
// 運営のOPENAI_API_KEYや、通常のCodexホームを引き継がない。

let nextId = 1;
const pending = new Map();
const journal = new BoundedEventJournal(); // 自作。件数・寿命・サイズ上限つき

function call(method, params, timeoutMs = 10_000) {
  const id = nextId++;
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      pending.delete(id);
      reject(new Error('RPC_TIMEOUT')); // 上流停止を意味しない
    }, timeoutMs);
    pending.set(id, { resolve, reject, timer }); // 送信より先に登録
    writeJsonLine(child.stdin, { id, method, params })
      .catch(failConnection); // 書き込みbackpressureも処理する自作ヘルパー
  });
}

function onMessage(m) {
  if (m.method !== undefined) {
    if (m.id !== undefined) {
      // 承認・ツール入力など、サーバーからの要求。
      handleServerRequestWithDenyPolicy(m); // 固定版の型に合う拒否応答
    } else {
      journal.append(m); // 通知。awaitより前に来ても保持する
    }
    return;
  }
  const waiter = pending.get(m.id);
  if (!waiter) return; // timeout後の遅延応答は内部状態を復活させない
  pending.delete(m.id);
  clearTimeout(waiter.timer);
  if ('error' in m) waiter.reject(toSafeRpcError(m.error));
  else waiter.resolve(m.result);
}

readBoundedJsonLines(child.stdout, onMessage, failConnection);
child.once('error', failConnection);
child.once('exit', () => failConnection(new Error('CODEX_EXITED')));
// failConnectionは多重呼出し可能とし、pendingとjournalの全待機をrejectする。
// stderrは上限つきで消費し、全文をログ保存しない。

await call('initialize', {
  clientInfo: { name: 'call_to_past_poc', title: 'Call to the Past PoC', version: '0.1.0' },
});
await writeJsonLine(child.stdin, { method: 'initialized', params: {} });

補助関数の実装で省けないのは、JSONの行分割、巨大行の拒否、壊れたJSONでの接続失効、書込失敗時の待機解放、未対応のサーバー要求への応答です。stdoutを1チャンク＝1JSONとしてparseすると、分割受信で壊れます。サーバー要求を放置すると、ゲームが承認待ちのまま止まります。

拒否方法は要求の種類で異なるため、全部に架空の{ approved: false }を返してはいけません。既知の承認要求には生成型に沿った拒否を返し、未対応メソッドはプロトコルエラーとして扱います。予想外のツール要求が出た判断は失敗させ、設定も点検します。

4. ログインは「ゲーム認証」と別に扱う

ユーザーAのゲームCookieはAのプレイを特定します。一方、Codexログインはモデルを利用するアカウントを決めます。Cookieを発行しただけでCodexへログインしたことにはなりません。

async function connectAccount(gameOwner, worker) {
  assertOwner(gameOwner, worker.owner);
  const cursor = worker.journal.cursor(); // 通知取りこぼし防止
  const login = await worker.rpc.call('account/login/start', {
    type: 'chatgptDeviceCode',
  });

  // 自作の認証済みUIチャネル。同じ所有者にのみ送る。
  // トークンは送らない。URLは許可されたOpenAI認証先か検査する。
  showLoginToOwner(gameOwner, {
    verificationUrl: validateOfficialLoginUrl(login.verificationUrl),
    userCode: login.userCode,
  });

  try {
    const event = await worker.journal.waitAfter(cursor, m =>
      m.method === 'account/login/completed' &&
      m.params.loginId === login.loginId,
      { timeoutMs: 120_000 } // アプリ独自の待機上限。公式有効期限ではない
    );
    if (!event.params.success) throw new Error('LOGIN_FAILED');
    const account = await worker.rpc.call('account/read', {});
    requireChatGPTAccount(account); // 自作。固定版の戻り値型に合わせる
    await worker.rpc.call('account/rateLimits/read', {});
    worker.ready = true;
  } catch (error) {
    await bestEffort(() => worker.rpc.call('account/login/cancel', {
      loginId: login.loginId,
    }));
    await quarantineAndDestroy(worker); // 成功との競合もあるので再利用しない
    throw error;
  }
}

デバイスコード方式の入口と完了通知は公式に定義されています。利用できるアカウント・組織設定は実接続で確認します。コードやログイン用URLは本人への案内に限り、アクセスログや分析ログへ送らない設計です。公式認証RPC

ChatGPT認証を使うCodex処理と、APIキーを使うLive処理は別の請求経路です。モデル利用の資格情報をブラウザへ渡す必要はありません。ホスト運用では運営がその資格情報を預かる責任が生じます。公式認証の説明

5. 写真と状態を渡して、判断だけ返してもらう

PoCでは判断要求ごとに新しいthreadを作る案を推奨します。会話の継続性はゲームサーバーが必要な範囲だけ送ります。モデル側の古い推測が次の判断へ混ざりにくく、既存のResponses呼び出しに近い契約になります。thread生成のオーバーヘッドと利用量は比較が必要です。

const teachingSchema = { // 教材用。実装時は既存の判断スキーマを使う
  type: 'object',
  properties: {
    possible: { type: 'boolean' },
    reason: { type: 'string' },
  },
  required: ['possible', 'reason'],
  additionalProperties: false,
};

async function judge(worker, request, signal) {
  // 自作mutex。初期PoCでは1ワーカー1判断に限定する。
  return worker.serial.run(async () => {
    const photo = await writeValidatedPhoto(worker.tempDir, request.jpeg);
    let threadId;
    try {
      const started = await worker.rpc.call('thread/start', {
        model: worker.selectedModel, // model/listと許可リストで事前確認
        cwd: worker.workDir,
      });
      threadId = started.thread.id;
      const cursor = worker.journal.cursor();

      const accepted = await worker.rpc.call('turn/start', {
        threadId,
        input: [
          { type: 'text', text: makeMinimalJudgmentPrompt(request.snapshot) },
          { type: 'localImage', path: photo.absolutePath },
        ],
        outputSchema: teachingSchema,
      });
      const result = await collectFinal(worker, cursor, {
        threadId, turnId: accepted.turn.id, signal,
      });
      return validateTeachingDecision(JSON.parse(result));
    } finally {
      // helperは未完了ターンがあれば中断・停止確認してから写真を削除する。
      // 停止確認できなければワーカーを失効させて終了する。
      await finishRequestResources(worker, { threadId, photo });
    }
  });
}

画像入力とoutputSchemaは公式インターフェースです。上の例では認証済みURLを外へ公開する代わりに、ワーカー内の一時画像を使います。localImage.pathはApp Serverが動いているマシン／コンテナのパスです。スマホ内のファイルパスではありません。写真は許可形式・サイズを検証し、ランダム名で保存します。

この例は、起動前に隔離と権限制限を済ませたワーカーを前提にしています。thread/startの短いコードだけで安全なワーカーになるわけではありません。instructionsの優先順位を持つフィールド、sandbox、ツール無効化などの具体的な設定名は固定版の生成型と設定仕様で確定させます。プロンプトの「ツールを使うな」だけに依存しません。

outputSchemaは出力の形を指定します。写真に見えない物を捏造していないか、在庫にない道具を使っていないか、クリア条件を満たしているかはゲーム側で検証します。possible: trueという教材用の値だけで実ゲームの状態を更新しません。

6. 通知から結果を集める

次のcollectFinalは自作ヘルパーです。RPCの正式なメソッド名ではありません。受け付けたturnの通知だけを拾い、itemの最終内容を保持し、turnの成功終了を確認してから結果を返します。

async function collectFinal(worker, cursor, ctx) {
  const completedItems = new Map();
  try {
    for await (const m of worker.journal.streamAfter(cursor, {
      timeoutMs: 30_000, signal: ctx.signal,
    })) {
      if (!belongsTo(m, ctx.threadId, ctx.turnId)) continue;
      // belongsToは通知別の型で判定する。
      // item通知: params.turnId、turn完了: params.turn.id

      if (m.method === 'item/completed') {
        completedItems.set(m.params.item.id, m.params.item);
      }
      if (m.method !== 'turn/completed') continue;
      if (m.params.turn.status !== 'completed') {
        throw new Error('TURN_NOT_SUCCESSFUL');
      }
      // バージョンにより完了turnに含まれるitemsもIDで統合する。
      mergeAvailableCompletedItems(completedItems, m.params.turn);
      return selectSingleFinalJsonText(completedItems);
    }
    throw new Error('EVENT_STREAM_CLOSED');
  } catch (error) {
    await interruptAndConfirmOrKill(worker, ctx);
    throw error;
  }
}

// 自作選択ルール：
// ・agentMessageを対象にし、phaseがあればfinal_answerだけを採用。
// ・commentary、ツール出力、途中deltaを結果としてparseしない。
// ・phaseがない版では、完了した候補が1つだけであることを要求する。
// ・空、複数候補、拒否、JSON不正は失敗として返す。
// ・item/completedの全文を使い、deltaと二重に連結しない。

イベントを待つ登録をawait turn/startの後だけに行うと、その間に届いた通知を失う可能性があります。ここでは送信前にcursorを取り、短いイベント履歴を再生できる設計です。履歴上限を超えて必要な通知が欠けた場合は「成功」と推測せず、失敗させます。

30秒はこのゲームに合わせたPoC側の例です。RPCの10秒、ログインの120秒とは別の期限です。待機のタイムアウトは上流停止ではありません。中断要求の応答も停止確認ではなく、完了通知の確認まで必要です。

7. 既存コードへどう接続するか

現行のcreateGameAIはAIResponsesClient.respondを受け取ります。structuredResponseはResponses形式からテキストを取り出してJSONとスキーマを検証します。最初はその契約を保つ薄いアダプターを置くと、ゲームロジックの変更を抑えられます。

// 提案するアダプター。新規ファイル案：packages/server/codex-judgment.ts
function makeCodexResponsesClient(worker) {
  return {
    async respond(body, signal) {
      const request = validateAllowedGameRequest(body);
      // instructions / input / schemaを明示的に変換する自作関数。
      const text = await runCodexJudgment(worker, {
        instructions: request.instructions,
        content: request.input,
        schema: request.text.format.schema,
        signal,
      });
      // ゲーム内部の既存パーサー向け互換形。上流の生レスポンスではない。
      return {
        status: 'completed',
        output: [{
          type: 'message',
          content: [{ type: 'output_text', text }],
        }],
      };
    },
  };
}

この注入例で移るのはcreateGameAI経路だけです。意図分類、ヒント、画像検査、エンディング文章などの別呼び出し元も、対象に含めるなら個別に接続します。「ゲームのAIを全移行した」とまとめないことが重要です。

8. 障害・中断・終了を先に設計する

状態扱い
turn/startの応答が来ない受付済みか不明。即再送しない。専用ワーカーを失効・停止し、元の処理を確定状態へ反映させない
利用枠不足／認証失効プレイを停止または再接続案内。運営APIへ自動フォールバックしない
JSON不正ゲーム状態は未更新。再試行をする層は1か所にする
ツール承認要求ゲーム判断に不要なら拒否して当該判断を失敗。承認UIを無期限に待たない
利用者が終了新規受付停止→実行中断→停止確認→ログアウト→ワーカー停止→保存物削除
プロセス異常終了全RPC・イベント待機を失敗させる。再起動時も失敗した操作を自動で二重実行しない
async function interruptAndConfirmOrKill(worker, { threadId, turnId }) {
  worker.accepting = false;
  const cursor = worker.journal.cursor();
  try {
    await worker.rpc.call('turn/interrupt', { threadId, turnId });
    await worker.journal.waitAfter(cursor, m =>
      isTerminalTurn(m, threadId, turnId), { timeoutMs: 3_000 });
    // completedとの競合もあり得る。キャンセル済み要求の結果は採用しない。
  } catch {
    await terminateIsolatedWorker(worker); // OS/コンテナ単位で子孫も終了
  }
}

async function closePlay(worker) {
  worker.accepting = false;
  await stopActiveTurnOrKill(worker);
  await bestEffort(() => worker.rpc.call('account/logout', {}));
  await terminateIsolatedWorker(worker);
  await removeOwnedWorkspace(worker); // 登録済み専用パスだけ。ユーザー入力は禁止
}

既存のstructuredResponseには、対象エラーに対して最大1回の修復再試行があります。アダプターでも2回、RPCでも3回、と重ねると意図せず実行回数が増えます。既存の再試行判定に、認証・枠切れ・中断・状態不明のエラーが混入しないよう対応表を作ります。

ログアウトは写真と履歴の全削除を意味しません。専用の認証保存先、OSの資格情報ストア、履歴、バックアップを含む保存先をPoCで調べます。CODEX_HOMEを分けるだけではプロセスのファイル読取権限やOS資格情報ストアまで隔離されない点に注意します。

9. 多人数・スマホへ広げるときの境界

所有者A→Worker A／認証A／領域A
所有者B→Worker B／認証B／領域B

最初の設計では、1プレイに1専用ワーカーを割り当て、終了時に廃棄します。利用者1人の複数プレイで認証を再利用する最適化は、所有権と保存期間の設計後に検討します。共有プロセスでログインアカウントを次々に切り替える実装は避けます。

ブラウザへ公開するのは「ログイン開始」「状態確認」「写真送信」「終了」などのゲーム操作だけです。RPCメソッド名やcwdをリクエストに指定させません。App Serverにはゲームに不要なファイル・コマンド操作もあるためです。

本人PC方式では、PC側ブリッジが運営サーバーへ外向きの認証済み接続を張り、短期ペアリングでプレイと結び付けます。スマホのlocalhostはPCではありません。ホスト方式では、ゲームサーバーと専用ワーカーの間を内部stdioにし、外部のHTTPS認証をゲーム側で扱うと境界が明確です。通信の暗号化だけで本人PC上の判断の改変を防げるわけではありません。

権限は固定版に合わせて、不要なツール・MCP・プラグイン・外部ネットワークを制限し、専用の読取範囲に閉じます。モデル上流への必要な通信は確保します。read-onlyでも任意ファイル読取が可能な設定なら不十分です。

10. 何ができればPoC成功か

段階確認成功条件
課金なしの通信テスト偽の子プロセスで通知先着・分割JSON・異常終了・タイムアウトを再現取りこぼし、待機漏れ、二重完了がない
アダプターテスト成功／拒否／JSON不正／中断を既存パーサーへ入力成功だけが検証へ進み、再試行は定めた回数内
状態テスト同一requestId、version更新後の遅延結果、終了後の通知ゲーム更新が1回だけ、古い結果は不採用
実アカウント1名ログイン→写真判断→JSON→終了本人枠で実行し、モデル利用と待ち時間を確認
2アカウント同時実行・片方のログアウト・保存物検査認証・写真・通知が混線しない
実スマホ＋Live音声委譲→Codex判断→事実反映→発話ゲームのテンポと終了制御を維持
