対象：現行Webゲーム ／ 調査・実装方針のみ ／ 実接続・課金検証は未実施

結論：部分移行は技術的に有望。全費用のサブスク化は未確認

まず、写真認識・意図分類・ゲーム判断をプレイヤー自身のCodexへ委譲する小規模PoCを推奨します。GPT-Live音声、現行の画像生成、fal動画、ホスティングは、初期案では運営負担として残します。

「自分のCodexを独自UIで使う」構成と、「一般公開ゲームが多数の人のアカウントを預かって動く」構成では、運用と認証の難しさが違います。社内のダッシュボード事例は前者の参考になりますが、後者の成立をそのまま保証しません。

採用判断を変える重要な制約

公式App Server資料には “experimental and aren't supported for production workloads” との記載があります。現時点では公開版の基盤を全面置換する判断は勧めません。これは技術的に接続できないという意味ではなく、安定運用の保証を前提にできないという意味です。[1]

1. 背景と仕組み

目的は、運営が全員分の従量課金を負担する構成から、本人の利用枠を使う構成へ移し、運営費の変動を抑えることです。App ServerはCodexを外部UIから操作するインターフェースであり、APIの請求先を切り替える汎用プロキシではありません。

スマホ／Web UI→ゲームサーバー→本人専用Codex→本人の利用枠

CodexにはChatGPTログインによるサブスク利用と、APIキーによる従量利用があります。後者でApp Serverを動かしても費用移転にはなりません。ChatGPTのログイン情報を、既存のResponses／Live APIのBearer値へ差し替える方式も採用しません。認証方式ごとに利用する製品と請求経路が異なります。[2]

プレイヤー側も無制限ではありません。Codexの利用枠は普段の利用と共有され、モデル・文脈・ツール利用で消費量が変わります。契約によって追加クレジットや組織課金もあり、「本人に追加請求が絶対にない」とは約束できません。利用可能プラン、残量、所属組織の設定を開始時に確認する設計が必要です。[3]

2. 現行コードとの照合：何を移せるか

モデル名はソースの既定値です。秘密設定・本番環境は読んでいないため、実稼働モデルや機能の有効状態を断定しません。

処理現行の接続・既定値サブスク移行の判定

生成画像の整合性検査、エンディング文章・設計Responses／検査はLuna次の候補同じく判断処理として委譲可能性が高い。初期の移行範囲に含めるかを明示する。
リアルタイム音声live/sessions／gpt-live-1初期案はAPI維持既存Web音声をサブスク認証で作成・制御する公開手順は今回確認できず。
場面画像・エンディング静止画images/generations・images/edits／gpt-image-2.5-flare追加検証候補Codex内蔵画像生成は存在。ただし現行モデル・APIと同じ契約ではない。
H3エンディング動画fal／minimax/h3-max-turbo/image-to-video現行経路は削減なし別事業者のFAL_KEYを使用。Codexにツールとして呼ばせてもfal側の費用は残る。
サーバー、保存、配信統合サーバーとホスティング残る／増える可能性利用者別Codex実行環境のCPU・メモリ・保守が追加される。

現行のGPT-Liveは delegation: { type: 'client' } を使っています。音声を維持したまま、委譲先の判断処理をCodexへ置き換える境界がある点は有利です。公式Live資料でも、クライアント委譲は任意のバックエンドを接続する方式として説明されています。[4]

音声と画像を「不可能」と断定しない理由

公式のChatGPT VoiceはGPT-Liveを使い、対応プランとデスクトップ／ペアリングしたiOSで提供されています。ただし、その製品機能の存在は、独自Webゲームに同じ接続を埋め込める根拠にはなりません。音声入出力だけでなく、割り込み、委譲、サーバーからの事実注入、終了処理まで互換性を確認する必要があります。[5]

内蔵画像生成は公式にCodex利用枠を消費する機能として説明されています。資料上はgpt-image-2で、現行のFlareと相違します。App Server単体での利用可否、結果ファイルの受け取り、参照画像編集、サイズ、生成時間、枠消費を確認できれば削減範囲を広げられます。現段階の確実な削減額には算入しません。[6]

C. Codex／ChatGPT内でゲームを実行公式アプリ内の会話・写真・音声を使う内蔵機能を活用する余地が大きい。現在の独自Web UI、時計、音声演出と同じ体験にはならない。別モードとして検討
D. 運営の1アカウントを全員で共用ログイン不要運営の利用枠へ集中するため、本人負担という目的を満たさない。利用者の分離も解決しない。不採用

Aでは、本人PCのブリッジから運営へ外向きの認証済み接続を張り、プレイ専用の短期ペアリングで結び付ける設計を推奨します。スマホからPCのlocalhostは参照できないため、localhost接続だけでは成立しません。Bでは、ブラウザからApp Serverの全RPCを直接公開せず、ゲームサーバーが必要な処理だけを中継します。

Bの前提確認：公開サービスが各利用者のCodexログインを受け付ける提供形態について、今回の公式技術資料だけでは許諾・本番サポートを確定できません。「禁止されている」とも断定しません。一般公開前に、第三者ゲーム用途、ホスト側のトークン保持、許容されるログイン方式、アカウント別課金の扱いをOpenAIへ具体的に確認する項目です。今回、問い合わせやログイン操作は行っていません。

4. 認証と実行の実装方針

以下は提案であり、実装済みではありません。公式RPCにはログイン、アカウント確認、利用枠取得、スレッド／ターン操作、画像入力、構造化出力があります。外部トークン方式は認証ライフサイクルを既に管理するホスト向けの実験的機能で、誰でも使えるOAuth登録手段の保証ではありません。[1]

① 利用者と専用ワーカーを結ぶ

ゲーム用Cookieとランダムなログイン試行IDを結び付ける。本人専用プロセス・CODEX_HOME・一時ディレクトリを用意し、他人の認証／履歴／写真を共有しない。スレッドを分けるだけでアカウント分離できると仮定しない。

② 公式ログインフローを完了

initialize → initialized → account/login/start。PoCでは chatgptDeviceCode を候補にし、利用資格や組織設定で使えるか確認。パスワードはOpenAI側に入力する。PCで成功したlocalhostコールバックがスマホでも成立すると考えない。

③ 本人確認・モデル・利用枠を検査

account/read、account/rateLimits/read、model/list を用いて実際のログイン状態と利用可能モデルを確認。APIキーモードを誤使用していないか確認。開始時の残量だけでプレイ完走は保証せず、途中の枯渇も扱う。

④ 判断要求だけを変換

thread/start と turn/start に、必要最小限の確定状態・会話・写真を渡し、outputSchema で既存の結果形式を要求する。最終応答と完了を待ち、既存スキーマで再検証してゲーム状態へ適用する。途中の自然文を判定結果にしない。

⑤ 終了・切断・枠切れを処理

requestId／playId／状態バージョンを保持し、重複と遅延結果を除外。タイムアウト時は中断し、失敗時に無断で運営APIへ切り替えない。ログアウト後はワーカー、認証、履歴、写真を廃棄。追加クレジット購入やリセットを自動実行しない。

ワーカーは固定バージョンから型定義を生成し、まずサーバー内部のstdioで接続する案です。不要なシェル・ネットワーク・MCP・プラグインは無効化し、ゲームデータだけを渡します。単なるread-only設定では広い読取権限が残り得るため、コンテナ境界と読取範囲も制限します。これは本番サポートの問題を解消する措置ではありません。

5. どれだけ削減できるか

実測の費用内訳がないため、削減率を数値で断定できません。API呼び出し回数の上限とドル建て費用は別です。ゲーム内の「クレジット」もCodex／ChatGPTの課金クレジットとは別物です。

月間の損益モデル

現状 = N × (J + L + I + V) + H
移行後 = N × ((1 − r) × J + L + I + V + W) + H + ΔH
運営の削減額 = N × (r × J − W) − ΔH
導入費の回収月数 = 導入費 ÷ 月間削減額（削減額が正の場合）

N：月間プレイ数、J：移行対象の判断API費、L：Live費、I：画像生成費、V：動画費、H：現状のホスト費。r：判断処理の移行割合、W：1プレイ当たりの追加ワーカー費、ΔH：固定の追加運用費。再試行・失敗分も各費用に含めます。

仮の内訳：1プレイ100単位判断費その他AI費判断を全移行した場合
メディア中心1090最大10%削減（追加費用を引く前）
中間3070最大30%削減（同上）
判断中心6040最大60%削減（同上）

この表は感度分析用の仮定であり、実測値・価格表・予測ではありません。画像を移せた場合は移行した画像費も加算できます。H3動画は現行fal経路のままなら加算できません。

本人の既存サブスク枠内に収まるなら、本人の追加支払いなしで運営の対象API費を減らせる可能性があります。しかし、仕事で使う枠の消費、ログインの手間、PC起動の手間がプレイヤー側へ移ります。新規加入を必要とする人には、少額のゲームAPI費を運営が負担する方が利用者全体として安い場合もあります。

先に測る項目

playIdごとに、モデル・処理種別・入力／出力／キャッシュ使用量・画像回数・Live利用量・動画課金対象・再試行を集計し、請求明細と照合します。本文・写真・認証情報は収集しません。代表的な難易度とプレイ時間で、平均だけでなく高コスト側も見ます。Codex側は利用前後の残量と失敗率を記録し、通常作業との共有枠を含めた実用性を評価します。

運営費の予測可能性だけが目的なら、Codex移行と並行して、永続的な日次／月次予算台帳、処理前の予算予約、生成回数制限、期限時のLive終了、許可した再試行だけの実行を検討すべきです。現状のメモリ上限は再起動で戻るため、金額の絶対上限ではありません。画像頻度や動画有効化の変更は体験要件として別途判断します。

6. 実装順序と採否基準

Phase 0 — 費用を分解する

代表プレイの実課金内訳を採取。移行対象費が追加運用費より十分大きいか確認。小さい場合は移行を止め、予算制御を優先。

Phase 1 — 本人アカウント1名で判断PoC

ゲーム本体と分離した固定バージョンのApp Serverで、写真＋確定状態→検証可能なJSONを試す。ゲーム用のAPIキーなしで当該判断が成功するか、本人枠の消費、待ち時間、拒否、枠切れを確認。APIと同じ入力で判断を比較する。

Phase 2 — 2アカウントとスマホの接続PoC

A/Bを選び、本人アカウントでのログイン、同時実行の非混線、別タブ、ログアウト、再起動、資格情報削除を検証。スマホ単独を採用条件にするならBのログイン完走を必須にする。

Phase 3 — 小規模な実ゲーム比較

GPT-Liveを維持し、判断処理だけ差し替える。既存30秒タイムアウトに収まるか、会話のテンポが許容できるか、実スマホで比較。制限到達で運営課金へ流れないことを確認。

Phase 4 — メディアの拡張可否を判断

画像生成の結果取得とモデル変更による品質を個別評価。音声は公式に利用可能な接続方式とゲーム制御との適合性が確認できてから扱う。公開運用は提供条件と実験的機能への依存を解決できるかで再判断。

開発に進む場合は新規機能としてspec→plan→tasksを作成します。本レポートは採用承認や仕様確定を意味しません。まず判断PoCに限れば、現行の音声体験を維持したまま費用移転の核心を検証できます。
