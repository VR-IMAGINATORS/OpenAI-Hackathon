# 会話履歴・状況画像つき本編の試遊

作業ブランチ: codex/game-core。PR先はdevelop。mainへのマージはAWS配置を起動する。

## 起動

PCは `npm run dev` → http://127.0.0.1:5173。スマホは `npm run play:mobile` → ターミナルのQRコード。
既存プロセスはCtrl+Cで終了してから再起動する。両方とも.env.localの設定を読み、統合サーバーを起動する。別の中継サーバーは不要。

.env.local.exampleの画像関連設定を参照。ローカルは画像設定省略時も初期値で動く。AI_MODE=liveと既存APIキー/予算/合言葉が必要。キーを文書や会話へ貼らない。mockは画面用で音声AIに接続しない。

画像にはIMAGE_MODEL=gpt-image-2.5-flare、検査にはIMAGE_INSPECTION_MODEL=gpt-5.6-lunaを使う。実アカウントでの利用可否は実機確認が必要。画像だけが失敗した場合もゲームは続く。

## 確認する体験

1. 参加時に日本語/英語を選択し「体験を始める」。導入動画の終了または右下のSkipでCalling画面へ進む。「応答する」を押すと着信音が止まり、マイク許可・プレイ作成・Live接続を行う。プレイ中の言語は固定。
2. 接続完了で本編と時計が始まり、現在の状況画像を並行して生成する。AIが未来の自分を助ける役割と写真から道具を具現化する仕組みを説明する。追加のプレイ開始ボタンはなく、そのまま写真を送れる。自分とAIの発話は左右の会話履歴へ表示される。
3. 撮影してプレビューを確認し送信する。認識完了後に用途を聞かれる。
4. 相談では行動を消費しない。明示指示で短い受諾音声から行動へ進む。
5. 開始/各行動結果に画像受信枠ができる。生成・検査中も会話できる。架空の進捗%は出さない。
6. 合格画像は対応する過去のメッセージへ表示される。失敗時は「未来から画像の受信に失敗しました」。再生成はサーバー側で最大1回、手動再試行はない。
7. 勝敗後の音声は最大12秒。その後も同じ画面で遅れて届く画像を見られる。

結果は終了から最大5分。容量制限・サーバー再起動で早期に消える場合がある。再プレイは別のplayIdとなり、旧画像が新しい会話に混ざらない。

## 編集する場所

- config/game-core.json: conversation.ja/en.openingMessageで着信応答直後の説明、liveInstructionsで役割・共通会話指示、分類例、物理判定・画像検査方針、表示グループ間隔。
- scenarios/mobile-playtest.json: 日英シナリオ、factsと許可遷移、人物/画風、必須/禁止の画像条件。
- apps/local-server/hosted-runtime.ts: 音声受付→分類→一度だけ行動→表示への接続。
- apps/server/result-store.ts: 履歴・サムネイル・検査済み画像・結果保持。
- apps/server/scene-jobs.ts / packages/server/image-service.ts: 画像生成待機、生成、重大矛盾検査、再試行。
- apps/web/src/ChatFeed.tsx / PlayScreen.tsx: 会話と写真、画像状態の表示。

JSON保存は次の新規プレイから有効。進行中は開始時snapshotを維持する。AWSへはリポジトリと配置の更新で反映。

ENABLE_GAME_TRACE=1はローカル開発専用。自分のプレイのGET /api/play/traceに短い解釈/判定理由/設定digest/時間を返す。写真・全文promptは含まない。終了時に破棄しproductionでは404。

## 負荷と配置

生成同時2、検査同時2、1プレイ1画像ジョブ、待機30件。生成は初期5回/分で、画像が会話より大幅に遅れる場合がある。各ジョブの待機込み期限は150秒。生成/検査の各試行は開始時に回数を数える。

本番配置前にGitHub EnvironmentへAI_GLOBAL_IMAGE_ATTEMPTSとAI_GLOBAL_INSPECTION_ATTEMPTSを追加する（初期案は各100）。deployツールとworkflowは新しい画像モデル/上限/結果保持設定を運ぶ。未設定なら配置準備で停止する。今回の作業ブランチPUSHではAWSを更新しない。

運営drainは画像待機を破棄し上流通信を中止する。通信中止がAPI提供側の課金停止を保証するものではない。実生成品質、会話テンポ、実スマホ、AWS5人同時の負荷は模擬テストと分けて確認する。

## メッセンジャーに統合した操作欄（2026-09-13）

本編は1つのメッセンジャー画面内に表示する。上部は相手・通話状態・終了アイコン、中央は会話履歴、下部はカメラ・写真ライブラリ・音声案内・送信アイコン。撮影後のプレビューと取り消し、送信失敗時の再試行も下部に表示する。送信済み写真は入力欄に残さず、会話履歴に表示する。

残り時間・行動回数は上部の情報欄、状況詳細と持ち物は同じ欄を開いて確認する。終了後の再プレイもアプリ内に表示する。AWSへの配置対応は保留中。

## 行動しない場合の診断

ローカルの.env.localでENABLE_GAME_TRACE=1としてサーバーを再起動する。新規プレイで現象が出た直後、終了前にメッセンジャー上部の状況欄を開き「診断JSONを保存」を押す。写真認識数、ユーザー発話の受信数、委譲の到着・待機・失効、分類と行動判定の段階を記録する。写真・認証情報は含めない。既存の成功行動traceには解釈と短い判定理由が含まれる。productionでは無効、プレイ終了時に破棄する。

2026-09-13: 無応答の原因は未特定。診断追加後のbuild/型検査成功、175テスト成功。診断なし・委譲未着・wait・期限切れ・終了時破棄を検証済み。

## ハーネスの回復と残り時間通知（2026-09-14）

相談の返答は分類理由とは別のanswerを使い、公開中の状況を根拠にする。行動の「やってみる」は予約後、結果は状態確定後に通知し、続けて現在の状況を伝える。長い状態情報も通知上限に合わせて分割し、後半の状況を切り捨てない。

委譲が届かない未処理発話を3秒後から読み取り専用で確認する（同一文脈一度、最大10秒に一度）。明示的な実行指示の場合だけLiveへ委譲を促す。監視から行動は実行しない。通常の委譲は20秒、再委譲の回復待ちも20秒で再発話を案内する。これは3秒の沈黙で指示を確定する仕様ではない。読み取り専用の確認にも通常のResponses予算を使う。

config/game-core.json の timeWarning で通知を変更できる。新規プレイから適用される。

- enabled: 通知の有効/無効。省略した旧設定では無効。
- thresholdSeconds: 通知する残り秒数。初期値60、指定秒数未満になったら一度。
- message.ja / message.en: 通知内容。{thresholdSeconds} は設定秒数に置換する。
- deliveryInstructions.ja / deliveryInstructions.en: この通知での口調。初期値は焦りを感じる短い案内。

時計が停止しているAI判定中・接続回復中には通知せず、進行再開後に判定する。音声通知とチャット表示を行い、再接続しても同一プレイで再通知しない。音声モデルの受領は発話・再生完了の保証ではない。時間切れは引き続きサーバーの時計で確定する。

### 手動確認

サーバーを再起動し、新しいプレイで確認する。

1. PCとスマホでハサミを送り「これで縄を切って」。一度の行動結果、状況の説明、結果画像の枠が出る。
2. 「今どういう状況？」と聞く。分類理由ではなく、現在の状況を答える。
3. 「切れるかな？」という相談や「いや、まだ切らない」という訂正だけでは行動回数が減らない。
4. 残り1分を切るまで待つ。焦った口調の通知とチャット表示が一度出る。必要なら試遊用設定のthresholdSecondsを大きくして早めに確認する。
5. 音声を再接続しても同じ時間通知を繰り返さない。

模擬APIの自動テストと実Liveの声・テンポの確認は別。今回、実API・PC/スマホの音声試遊・AWSデプロイは未実施。
