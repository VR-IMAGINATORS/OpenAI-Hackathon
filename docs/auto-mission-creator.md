# 自動ミッション生成プロトタイプ

AIが新しい脱出ギミックを考え、その解法が固定ルール内で成立するかを評価する独立CLIです。最終案・解法・指摘・反証・所要時間をJSONとダークテーマのHTMLへ保存します。現在のWebゲーム、GPT-Live、AWSには接続しておらず、このCLIで合格してもゲームへ自動登録されません。

仕様は [spec.md](../specs/auto-mission-creator/spec.md)、構成は [plan.md](../specs/auto-mission-creator/plan.md)、内部データの正本は [schemas.ts](../tools/auto-mission/schemas.ts) です。

## 最初に試す

Node.js 22.12以上とインストール済みの依存関係が必要です。リポジトリのルートで実行します。以下はWindows PowerShell向けに、引数を保持することを確認した `npm.cmd` を使用します。macOS/Linuxでは `npm` に置き換えてください。

```powershell
npm.cmd run mission -- generate --config config/auto-mission/default.json --mock
```

終了時に表示された `report.html` をブラウザで開いてください。出力先は `runs/auto-mission/<UUID>/` です。各実行は別のディレクトリへ保存され、`runs/` はGit管理対象外です。

`--mock` は固定fixtureを使い、APIへ通信しません。保存・修正ループ・判定・表示を確認するためのモードであり、新しいストーリーの生成品質や実AIの判断精度を確認した結果ではありません。独自設定の生成を評価するときは `--live` を使用します。

## 実際のモデルで生成する

`OPENAI_API_KEY` を現在のプロセスの環境変数、またはリポジトリの `.env.local` に設定します。すでに存在する環境変数が優先されます。ルートの `.env` は読みません。キーを企画資料・設定JSON・Gitへ含めないでください。

```powershell
npm.cmd run mission -- generate --config config/auto-mission/default.json --live
```

`--live` は有料APIを呼び出します。Astraが利用できない場合は失敗として終了し、下位モデルへ自動変更しません。ブラウザや審査員にキーを渡す仕組みではなく、開発者のローカルCLIで実行するプロトタイプです。

生成処理は次の順番です。

1. 外部設定を検査し、Astraで初期状況・事実・達成条件のコントラクトを生成する。
2. コードと独立したAstra呼び出しでコントラクトを検査し、合格後にdigestで固定する。
3. Astraでストーリーと構造化解法を生成する。
4. コードで道具の所在・状態変化・回数・順序・時間見積りを検査する。
5. 通過した案を3つの独立した視点で評価し、Astraが指摘と反証を検証する。
6. コードが合否を決める。不成立なら同じコントラクトで最大2回修正し、毎回すべて再検査する。

機械検査の失敗、評価の欠落、不明な判定、未解決の指摘を多数決で合格へ変更しません。失敗時は「生成できませんでした」と表示し、作成できた最終案と失敗理由を保存します。人間の承認待ち状態はありません。

## 保存した案を再評価する

`<UUID>` は前回表示された出力ディレクトリに置き換えます。

```powershell
npm.cmd run mission -- evaluate --input runs/auto-mission/<UUID>/run.json --live
```

保存済みの最後の候補と固定コントラクトを、新しい実行結果として再評価します。候補を新しく生成したり、失敗後に修正したりはしません。モデル・上限などには保存済みの設定スナップショットを使用するため、`evaluate` に `--config` は指定しません。`--mock` へ置き換えれば課金なしで経路を確認できます。

APIを使わずHTMLだけ作り直す場合:

```powershell
npm.cmd run mission -- render --input runs/auto-mission/<UUID>/run.json
```

`render` は保存JSONを読み、新しい出力ディレクトリにレポートを作ります。元の結果の合否・測定値は変えず、新しく評価したとは扱いません。

## 既知のケースで評価を比較する

```powershell
npm.cmd run mission -- benchmark --config config/auto-mission/default.json --mock
npm.cmd run mission -- benchmark --config config/auto-mission/default.json --live
```

`tests/fixtures/auto-mission/` の正常1件と異常4件を順番に評価します。

| ケース            | 意図                                 |
| ----------------- | ------------------------------------ |
| valid             | 身近な道具で解ける例                 |
| action-limit      | 必要な行動数が上限を超える           |
| spent-tool        | 使用不能になった道具を再利用する     |
| bound-body        | 手が使えない拘束状態で道具を操作する |
| missing-placement | 物の具現化場所・受け取り方法が不明   |

正解ラベルと期待理由は比較用の情報で、モデルの入力に渡しません。ベンチマークの世界観・道具・難易度は各fixtureの固定条件を使い、指定configからはモデル・予算設定を採用します。回数不足・使用不能の再利用は機械検査、身体動作や説明の不足はAI評価での検出を確認するケースです。

API呼び出し回数・出力token・経過時間の上限は、ベンチマーク全体で共有します。ケースごとに上限が増えるわけではありません。予算や時間が尽きれば途中で止まるため、`benchmark.json` の `complete` と各ケースの結果を確認してください。個別レポートも保存されます。少数の固定ケースでの結果を、一般的な精度や面白さの保証とは扱いません。

## 調整するファイル

初期設定は [config/auto-mission/default.json](../config/auto-mission/default.json) です。コピーしたJSONを `--config` で指定できます。

| フィールド                  | 調整内容                                       |
| --------------------------- | ---------------------------------------------- |
| world                       | 世界観と守る制約                               |
| difficulty.obstacleCount    | ギミック数。2〜5、初期3                        |
| difficulty.maxPhotoSends    | 写真の送信回数。初期4                          |
| difficulty.maxPhotosPerSend | 1送信の枚数。初期2                             |
| difficulty.maxActions       | 行動上限。初期nullは上限なし、集計は実施       |
| difficulty.totalTimeSeconds | ゲーム内の手順見積り時間。初期300秒            |
| objectCatalog               | 解法例に使える身近な道具と通常の性質           |
| referenceScenarios          | 明示的に読み込むローカル参考資料のパス         |
| models                      | 役割別のモデル・reasoningEffort・出力token上限 |
| limits                      | 修正回数、API予算、実行時間、入力サイズの上限  |

道具リストは最低一つの解法が存在するかを検証するための入力であり、将来のゲームで別解を禁止するものではありません。`send` は送信1回、`use`・`place`・`retrieve`・`move` はそれぞれ1行動としてコードが集計します。設置した物は移動に追従せず、回収手順が必要です。 `use` は、固定コントラクトにある扉を素手で開けるなど、具現化した道具を使わない通常の操作にも使用できます。この場合は `itemIds` と `itemEffects` を空にし、宣言済みの事実だけを変更します。身体的に実行できるかは引き続き独立評価で確認します。`send`・`place`・`retrieve` には対象の道具が必要です。

生成・評価プロンプトは [tools/auto-mission/prompts/](../tools/auto-mission/prompts/) にあります。

| プロンプト            | 用途・初期モデル                        |
| --------------------- | --------------------------------------- |
| common.md             | 全役割の共通制約                        |
| contract-generator.md | 初期条件の生成・gpt-6-astra             |
| contract-checker.md   | 初期条件の独立検証・gpt-6-astra         |
| story-generator.md    | ストーリーと解法の生成・gpt-6-astra     |
| repairer.md           | 固定条件を守った修正・gpt-6-astra       |
| physics.md            | 身体・物理の評価・gpt-5.6-sol           |
| resources.md          | 道具・回数・時間の評価・gpt-5.6-luna    |
| causality.md          | 因果関係・説明不足の評価・gpt-5.6-terra |
| verifier.md           | 指摘の検証・反証・全体確認・gpt-6-astra |

生成・修正・検証の最上位要件は設定検査で確認します。初期allowlistはAstraのみです。生成・修正の初期reasoningEffortはmedium、固定条件検証と指摘検証はhighです（high生成は初回計測で出力上限に達したため）。3評価者へ他者の評価や前回の指摘を渡さず、個別の呼び出しとして実行します。

## 時間と予算の読み方

初期値は全体600秒、1呼び出し600秒、最大17呼び出し、出力合計100,000 token、最大2回修正です。個別呼び出しの期限は600秒と全体の残り時間の短い方です。全体期限は修正のたびにリセットしません。

**180秒は目標の生成所要時間、600秒は初回計測の打ち切り上限**です。600秒かかる前提でも、180秒以内に終わる保証でもありません。最初はコントラクト生成・検査・固定を先に行う構成を測定し、遅い段階を確認してから短縮を検討します。

レポートでは全体の実経過時間、各段階、各モデル呼び出し、修正回数を確認できます。並列3評価の呼び出し時間を足した値は、ユーザーが待った全体時間とは異なります。少数試行からp95や安定した応答時間を主張しません。

API予算は呼び出し前に予約するため、実使用量が少なく見えても、次の呼び出しに必要な最大出力枠が残っていなければ停止します。使用量不明は0とせず予約分を維持します。token予算は請求額の厳密な上限ではありません。

`estimatedSeconds` の合計は、生成されたゲーム内の動作見積りです。実APIの測定時間とは別で、プレイヤーの思考・撮影・音声やネットワーク待機を含む実プレイ時間を保証しません。

## 結果と限界

- 終了コード0: 成立性検査に合格。ベンチマークでは期待結果との一致。
- 終了コード1: ストーリー不成立、またはベンチマークで期待と不一致。
- 終了コード2: 設定不正・API・予算・保存などの実行エラー。

JSONは段階ごとに保存し、Ctrl+Cでも途中保存を試みます。ディスク障害やプロセスの強制終了では完全な保存を保証しません。HTMLには生成文を実行せず、文字列として表示します。

このプロトタイプで検証するのは成立可能性です。面白さ、実機音声、写真認識、本編との接続、生成失敗時の本編用フォールバックは対象外です。自動テストとmockの成功は、実AIの生成品質や実プレイの成功を意味しません。実APIの結果は各liveレポートで別途確認してください。

## 初回の検証結果

[実測記録](../specs/auto-mission-creator/measurement.md)に、失敗も含む段階別の所要時間と設定変更の理由を記録しています。

最新設定の単発実測では、Astra生成から最終検証まで約5分57秒、修正なしで合格しました。2〜3分の目標は未達です。非blockingな時間表記の不一致1件は評価履歴に残っています。
