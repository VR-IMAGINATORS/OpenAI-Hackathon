# 静止画のコラージュ化を防ぐ修正

日付: 2026-09-15。対象ブランチ: feature/shibuya/game-polish。

## 報告と原因の確認範囲

ユーザーから「動画には様々な場面を望むが、静止画は以前のように一つの場面を写してほしい」と指摘があり、修正を承認された。コラージュ化は意図した挙動ではない。報告対象の実画像・実際の生成promptを入手していないため、その一枚の直接原因は未確定。

コード上は、動画脚本と静止画指示を同じ要求で作りながら全アイテムの登場を求め、静止画の単一時点・単一視点と構図検査を明示していなかった。また、通常の場面画像へ行動前後の情報を並べて渡していた。前回の782件の成功は、実生成画像の構図の確認ではない。

## 修正

- 静止画共通の構図規則を追加。一つの場所・時点・カメラ視点で描き、コラージュ、コマ割り、別視点の挿入、使用前後の比較、複数時点の人物重複を禁止する。
- ゲーム中の通常・調査型画像、エンディングの開始・終了画像、回復用の余韻画像に適用する。画像検査では各コマの事実が正しくても構図違反を重大な不合格として扱う。通常の窓・鏡・画面などは一つの視点に自然に含まれる場合に許す。
- 通常の場面画像へ行動後のfacts・道具状態だけを渡す。開始画像の行動データは準備姿勢とその時点の道具状態、終了画像は成否と終了時の道具状態に整理する。
- 演出AIには、全アイテムの登場を動画全体で満たすよう明示。静止画の制約はstartPrompt/endPromptだけに限定し、動画の時系列の複数カットを維持する。静止画の編集には動画promptや対応表を渡さない。
- 元の全行動履歴、モデル・尺・解像度、通常の生成回数、検査回数の上限は維持。構図不合格は既存の修復・再生成枠を使い、改善しなければ公開しない。

## 検証

関連118件の課金なしテスト成功。全体テストは892件成功、失敗・skipなし。`npm run build`（型検査・標準設定検証・18種類のstory設定と調査型シナリオの検証・UI／サーバービルド）も成功。変更したTypeScriptのPrettierと`git diff --check`で形式も確認した。

- 通常・調査型の場面画像について、模擬上流から構図不合格を返し、既知の規則として受理、1回再生成、再度不合格なら非公開となることを確認。
- actions / aftermath / 回復用余韻の開始・終了画像に同じ構図規則を適用し、模擬の不合格理由が修復へ渡ることを確認。
- 状態の前後比較が静止画用データに残らず、動画用の元履歴には残ることを確認。未公開情報の非開示、失敗・損傷・消費済み状態の保持も既存テストで検証。
- 複数行動の動画promptと全アイテム対応表、通常の生成回数、40行動・40アイテム時の既存要求上限を確認。

これらは指示・データ経路・模擬検査結果の処理の検証であり、実モデルがコラージュを確実に避ける／検出するという実測ではない。実画像と動画の再生成、スマホでの視聴、追加生成時間の測定は未実施。追加の固定待機はないが、構図の検査不合格による再生成で待ち時間が増える場合があり、追加7秒以内とは保証しない。
