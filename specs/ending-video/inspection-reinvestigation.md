# エンディング画像検査の再調査

2026-09-14、初期画像のみの対応後も「開始・終了画像の内容を確認できませんでした」と報告された。当該プレイの固定エラーコード・画像・検査応答は未取得であり、そのプレイの直接原因は未確定。一方、今回の架空プレイによる実API検証では、正常な背景を追加の道具と誤認して開始・終了画像を拒否する問題を確認した。同じ画像を修正後の指示で再検査し、誤判定の解消と、実際の状態矛盾の拒否を確認した。

## 前回の調査・検証の不足

- 前回は終了時の画像選択と、余韻への分岐を直した。一方、画像生成と検査に渡すシナリオ定義の差分まで追えていなかった。
- 模擬テストは `exit=closed` など直接読める架空のfactを使い、画像検査のpass/rejectもテスト側で返していた。既定の `story-catalog.json` の内部ID・状態値・物理描写の対応を検証していなかった。
- 「自動テスト成功」と「実際の生成障害の解消」を分けて報告してはいたが、実生成を確認せずにユーザーへ再試遊を繰り返し依頼する進め方だった。

## 確認した不備と修正

| 不備 | 影響 | 対応 |
| --- | --- | --- |
| エンディング画像には全ギミックのfactsを渡し、本編画像の「登場済みだけ」の条件を使っていなかった | 未登場の装置まで生成・検査の対象になり得る | 本編と同じ公開範囲に絞った目標状態を開始・終了の時点ごとに作る |
| エンディング側にはfactのvisualDescriptionと検査rulesがなかった | 例えばpressure-latchという内部IDが目隠しの結びを表すことをAIへ伝えておらず、名前から別の装置を想像し得る | 同じ `sceneRules` から物理描写・対象状態・禁止変更を取得して、演出・画像生成・検査に渡す |
| 静止画で全履歴・全所持品・見えない仕組みまで確認させる余地があった | 実際の矛盾がなくても判定不能になり得る | 検査は見える重大な矛盾と必要な結果の証拠に絞る。隠れた顔や画面外の全所持品を描くよう要求しない |
| AI呼び出しの期限によるfetchのrejectを一般失敗として扱っていた | 内容の不合格と時間切れの切り分けが困難 | abortされた呼び出しを既存の期限エラーへ正規化する。送信回数や再送条件は変えない |
| 検査不合格・判定不能・応答未完了・応答不正・時間切れが同じ画面文言だった | 利用者の報告から原因を区別できない | 開始／終了画像と原因を分けて表示する。生のAI応答や認証情報は表示しない |
| 本編の画像保存前に `ready`・`assetId=null` を公開していた | 完成表示でも画像取得がHTTP 400になり、終了時の素材収集には入らない瞬間がある | 保存中はcheckingのままとし、画像IDの保存後にreadyを同時に公開する |
| 空の所持品を「室内にも物がない」と解釈し、初期画像からある端末や箱を未提示の道具と判定していた | 実APIで開始・終了画像とも不合格になり、同じ背景を消すための修正生成が必要になった | 所持品はプレイヤーが使える道具、参照画像にある背景は既存の室内物として区別する。背景を新たな攻略道具や脱出手段にすることは認めない |

最後の不備は前回の全体テストでも断続的に現れていたが、再実行で通ったとして残してしまっていた。今回、同じテスト群100件の反復で4件のHTTP 400を再現し、画像IDが不正であることを確認した。保存処理を明示的に保留するテストで、修正前に必ず `ready` / `assetId=null` が公開されることを再現した。これも当該の「画像検査」エラーの直接原因と断定するものではないが、実装上の別の確定不具合である。

未知の判定や不正応答を合格扱いにする変更はない。明確な画像検査不合格だけ1回修正でき、通信失敗・判定不能では再生成しない。fal送信前の内容検査、MP4検査、利用制限は維持する。

## 実APIで確認したこと

使用モデルはローカル設定どおり、画像 `gpt-image-2.5-flare`、検査 `gpt-5.6-luna`、文章・演出 `gpt-5.6-terra`。実際の `story-catalog.json` の構成0を使い、架空の0行動・0解除・時間切れを作成した。ユーザーの写真は使わず、生成した初期画像を本編の画像検査に通したうえで、製品と同じ文章・演出・画像生成・検査関数を呼び出した。

| 検証 | 実結果 |
| --- | --- |
| 初期画像生成と本編検査 | 合格。背景に端末と箱がある |
| 結末文・演出 | 完了。`aftermath`、`usedActionIds=[]` |
| 修正前の開始画像検査 | 背景の端末と箱を、空の所持品に反する未提示の道具として拒否 |
| 開始画像の修正生成と検査 | 1回の修正で合格 |
| 修正前の終了画像検査 | 同じ背景を「追加の装置」として拒否 |
| 終了画像の修正生成と検査 | 1回の修正で合格 |
| 背景・所持品の区別を加え、拒否された開始画像をそのまま再検査 | 合格。画像は再生成していない |
| 同じく拒否された終了画像をそのまま再検査 | 合格。画像は再生成していない |
| 対照試験：同じ画像に「目隠し全体の解除済み」という目標状態を与える | 目隠し・顎下の帯・結びが残る矛盾を正しく拒否 |

実呼び出しは累計画像5回、Responses10回（本編検査1、文章1、演出1、エンディング検査7）。エンディング検査7回はすべて構造化応答が完了し、所要時間3.5〜8.1秒、出力121〜579トークン（推論分込み）だった。今回は1000トークン・15秒の上限による失敗は観測していない。上限を増やす根拠にはせず、この設定を維持した。`max_output_tokens` が推論分も含むことは [OpenAI Responses API仕様](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) に対応する。

これは「任意の画像が必ず成功する」ことや、ユーザーが報告した過去の画像が同じ理由で失敗したことの証明ではない。実際に誤判定された同じ画像での修正前後の比較と、矛盾を拒否する対照試験の結果である。

## まだ確認が必要な点

- 当該プレイの `ENDING_START_INSPECTION_...` または `ENDING_END_INSPECTION_...` のコード。現状の画面文言だけでは、不合格だったか応答が不完全だったかも区別できない。
- 失敗行動・部分進展・道具の破損だけがある場合、および2解除／全解除で初期画像しか完成していない場合の実生成。
- その先の新しいfal動画生成と再生。今回の実検証ではまだfalを送信していない。実機音声・iPhoneでの再生も別途確認が必要。

## 検証方法

`tests/ending-inspection.test.ts` は既定のstory-catalog全18構成・2言語・7段階（0解除、各障害の部分進展、1／2／3解除）・3種類の画像履歴（初期のみ、最新のみで行動前が欠落、最新と行動前が完成）の756通りを確認する。未登場ギミックの説明が入力へ漏れないこと、opaqueなIDに物理描写が添うこと、解除・部分進展・破損が保たれること、画像の揃い方に応じた演出モード、APIリクエストのスキーマを確認する。別の画像生成経路テストで、開始行動前と終了時点の状態を混ぜず、背景・所持品の区別を生成と検査の両方へ届けることを確認する。モデル応答はここでは模擬であり、実生成の合格数には数えない。

修正後の `npm.cmd test` は406件成功、失敗・skipなし。`npm.cmd run build`（型・設定検証を含む）も成功。画像不足と終了時の締め切り、本文生成失敗、明確な検査不合格だけの1回修正、判定不能・通信失敗での再生成防止、falの重複送信防止、MP4の音声・時間・サイズ検査、動画取得のHTTP Rangeも既存のテスト群で確認した。`core-scene-http.test.ts` の保存保留テストは修正前に `ready` と `checking` の不一致で失敗し、修正後は公開状態・HTTP画像取得・エンディング素材の参照を確認して成功した。

ローカルの `artifacts/ending-inspection-audit/probe.ts` は、架空の0行動・時間切れプレイで本編と同じ開始画像生成・検査、結末文、演出、開始・終了画像の生成・検査を直接実行する。認証情報は `.env.local` からサーバー内で使用する。プレイヤーの写真は使わず、falは呼ばない。実呼び出しは累計画像5回・文章と検査10回に制限し、応答状態・時間・トークン数を記録する。

初回は具体的な外部送信・課金の明示承認がないとして自動承認審査に拒否された。その後、送信対象と累計上限を提示し、ユーザーの続行指示を受けて再審査が許可したため実行した。上限には到達したが超過していない。

追加検証の `artifacts/ending-inspection-audit/matrix.ts` は、上記の未検証3パターンを準備済み。初期画像を再利用して実画像を検査し、合格画像だけをfalへ送る。追加の累計上限は画像12回・Responses24回・動画3本（0行動、ノーマル、ハッピー）。送信前に台帳へ記録し、fal受付が曖昧な場合は再送しない。現時点では追加課金のユーザー回答待ちで、実行していない。各スクリプトと架空データの応答・画像はGit管理外のローカル調査成果物に保存する。認証情報・ヘッダー・ユーザーの写真は含めない。
