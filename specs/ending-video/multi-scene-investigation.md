# Codex版とWeb版の動画構成の比較

2026-09-15。Web版が単一場面へ偏るというユーザー報告を受け、リポジトリの両実装と公式資料を比較した。報告された実動画・送信プロンプトは手元になく、以下は実装の比較と原因の推定。Codex版の成功実績をWeb版の検証へ流用しない。

## 差の所在（修正前）

| 観点 | Codexスキル版 | Web版 |
| --- | --- | --- |
| 動画生成 | H3 Max Turbo I2V、15秒、768P、balanced、開始・終了画像 | 同じ標準設定。画質設定だけでは単一場面への偏りを説明できない |
| 行動範囲 | 原則直近2行動。1行動・余韻も比較 | 同じ直近最大2行動。全確定履歴は渡すが映像用IDは2件まで |
| 優先順位 | 2行動の因果と人物の演技を詳細に検討 | 道具による成功を最後の解除から優先し、1行動へ絞れると指示 |
| 撮影・編集 | H3資料を読み、各ショットの開始・動作・終点・音、道具の持ち替えを最終promptへ残す | 一般的にカメラとmotivated cutsを指示するだけで、ショット番号・カット時刻・行動別の場面が必須ではない |
| 両端の構図 | 脚本の開始と終幕に合わせる | 同じ1024-square compositionと指示。サイズの一致と構図の一致が曖昧 |
| 脚本の仕上げ | 自己点検に加え独立脚本レビューの手順がある | 1回の演出要求内で3候補とpromptを生成する |
| 画像不足・障害 | 保存した素材を確認し、必要な制作を会話で進める | 終了時に完成画像を固定。行動前参照や行動結果画像が不足すると余韻のみ。演出AIの一時失敗でも余韻の代替処理へ進む |
| 画像制作 | エンディングはimagegenで制作。両画像の同寸法を要求し、固定の正方形ではない | Flare low・1024正方形。検査で重大な事実矛盾を確認するが、面白さや複数カットの達成は検査しない |

コード: `apps/local-server/ending-ai.ts`、`apps/server/ending-jobs.ts`、`packages/server/ending-image-service.ts`、`packages/server/fal.ts`。Codex版: `.agents/skills/call-to-past/references/ending.md`、`scripts/media.py`、`scripts/generate_h3.py`。Webの演出モデルの既定値は `gpt-5.6-terra` だが環境設定で変更可能であり、稼働中環境の設定はこの調査で確認していない。

## 原因の推定と今回の修正

[MiniMax公式ガイド](https://huggingface.co/MiniMaxAI/MiniMax-H3/blob/main/docs/VIDEO_PROMPT_WRITING_GUIDE_base_en.md)の3.2節は、開始・終了画像方式は単一ショットに寄せ、複数ショットは明示した場合に使うとしている。4.2節はショット番号・切替時刻・切替先を書く形式を示している（2026-09-15確認）。Webの抽象的な編集指示と「最後の1行動」への優先順位は、報告された症状と整合する。2画像方式そのものが複数場面を禁止しているわけではない。

今回、既存の演出要求内で次を具体化した。

- `preferredSequenceActionIds` で最初の行動前参照がある直近2行動を時系列で提示する。少なくとも1件に画像根拠のある道具による成功がある場合に優先し、単独候補順位より先に接続案を検討する。
- 2行動なら「第1の方法と結果→カット→第2の方法と結果→結末と反応」を別ショットで要求する。単に同じ操作を別角度で見せる構成では2行動を満たさない。
- `[Shot 1]`、続くショット番号と15秒内のカット時刻を最終promptへ書く。例として0〜4秒、4〜8.5秒、8.5〜12秒を案内するが、動作に応じ調整し、文字は結末の後に出す。
- 同じ正方形サイズでも両端のカメラ位置・構図は変えてよいと明記。後で登場する道具の先出し、道具の変身、失敗の成功化、消耗品の復元を避ける。
- 1行動に絞る場合は時間・連続性の具体的な理由と省略対象を残す。余韻の制約・代替処理は維持する。

ショット形式はfalへ渡す単一のprompt文字列内の指示であり、新しいAPIフィールドではない。生成動画のショット数・時刻をサーバーが保証する変更ではない。

## 待ち時間・費用・デメリット

追加の画像待機・LLM要求・中間画像・動画POSTは0。正常系の演出要求1回、画像2回、検査2回、15秒動画1本を維持し、既存の再試行上限も増やさない。演出出力は4,096tokens以内のまま、比較文を短くして具体的なショット指示へ割り当てる。

この構造から、追加遅延はほぼ同等〜数秒を見込む。これは実測値ではなく、7秒以内の上限保証ではない。LLMの実出力長、画像生成・検査の再試行、混雑で変動する。モデル・尺・解像度は同じなので動画の設定に起因する単価増はないが、テキストtoken量や再試行数が変わるため実費の完全一致は保証しない。

複数の操作を15秒へ含めると、道具・手・姿勢のつながりが崩れる、各動作が短くなるリスクがある。参照不足のプレイは引き続き余韻になる。また、直近最大2行動の範囲なので、全3障害の再現を約束する修正ではない。

[fal公式API](https://fal.ai/models/minimax/h3-max-turbo/image-to-video/api)によるprompt書き換え時間はbalancedが約1秒、qualityが最大約30秒（2026-09-15確認）。qualityへの変更は最大約29秒増となり得るので採用しない。独立レビュー、シーン別動画、中間画像は追加生成工程が必要で、約7秒の条件を満たす根拠がないため今回に含めない。

## 検証

関連3ファイルの課金なしテスト56件が成功。拡張した演出テストでは、2成功、成功→失敗、全失敗、道具なし、最初／次の行動前参照不足、初期画像だけ、0行動を扱う。2件の時系列優先、既存の単独候補・余韻、要求のサイズ検証、1回の演出要求・2枚の参照・4,096出力tokensを確認した。

全体テストは776件成功、失敗・skipなし。`npm.cmd run build` が成功し、その中で型検査、標準JSON・全18構成の検証、UI・サーバービルドを確認した。変更したTypeScriptのPrettier検査と `git diff --check` も成功。AI応答・画像・動画・providerは模擬であり、この所要時間を実生成の遅延見積へ転用しない。

## 実生成で残る確認

実API動画・スマホ再生・総待ち時間の比較は未実施。同じ確定履歴・参照画像・設定で旧版と新版を比較し、次を確認する。

1. 異なる2つの攻略動作と各結果が読み取れるか。成功→失敗でも結果を捏造していないか。
2. カット間で道具・姿勢・位置が維持され、結末後にタイトルへ到達するか。
3. 演出開始から動画受信までの待ち時間と再試行回数を比較し、追加が約7秒を繰り返し超えないか。
