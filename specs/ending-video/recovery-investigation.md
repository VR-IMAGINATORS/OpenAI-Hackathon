# 画像・結末動画の失敗経路調査（2026-09-15）

状態: ユーザーが3方針を承認し、回復処理を実装・検証済み。[判断記録](../../.specworkflow/discussions/2026-09-15-ending-recovery.md)。

## 報告ログから分かること

- `ENDING_DIRECTION_TIMEOUT` は演出生成中の時間切れ。修正前は演出Responses最大30秒・1回で、失敗後の代替演出がなかった。1リクエストの時間切れと結末ジョブ全体の期限切れも同じコードにまとめていた。
- `PLAY_EXPIRED` は通常のプレイ操作権限の終了を示す。報告時のログには経路・プレイIDがなく、同じプレイか、画像失敗との因果関係があるかは確定できない。
- 途中画像の生成・検査はHTTPリクエストの外で動き、独立したメディア権限を持つ。失敗詳細は従来ログに出ず、画面では一律に受信失敗となる。ブラウザが完成画像のGETに失敗した場合も似た案内になる。
- 結末権限は正常終了時に予約され、通話の終了・通常プレイ権限の終了後も継続する。通常操作の `PLAY_EXPIRED` を無視して期限を延ばす必要はない。

## 承認・実装済みの判断

1. 演出AIのタイムアウト・不正応答時、確定状態だけから簡潔な余韻の演出を組み立て、実画像・実動画の生成へ進む。E19で、演出指示に限るE17の例外として定義した。
2. 一時的な画像生成・検査障害の自動再試行を、全体予算・期限内で許容する。追加画像の課金可能性は説明・承認済み。検査障害では生成済み画像を維持して再検査し、無駄な再生成を減らす。各画像最大2生成、各生成画像最大2検査。結末の検査は合計8回、途中画像は4回まで。
3. 終了時点で完成画像がゼロの場合だけ、文章生成と並行して終了から最大30秒、進行中の画像を待つ。既に1枚以上ある場合の締め切りは従来どおり。全画像失敗・キャンセル、全体期限、結果失効時は早く終了する。

安全検査の不合格を合格扱いにすること、未検査画像や模擬動画の公開、未確定の成功の創作は提案に含めない。

## 経路ごとの調査結果

| 経路 | 現状・今回の対応 |
| --- | --- |
| 通常プレイ操作の終了・復帰期限 | 終了後の操作は拒否する。所有者確認済みプレイIDとサーバー定義の経路をログへ追加。ヘッダーや本文は記録しない。 |
| 途中画像の生成失敗 | 既存の最大2試行は維持。生成・検査・予約失敗の原因分類をログへ追加。 |
| 途中画像の検査通信失敗 | 同じ画像を最大2回検査する。解消しなければ残りの生成枠で修復して再検査。最後の生成枠を使った後も、その画像を再検査できる。 |
| 途中画像の保存失敗 | 保存の段階をログへ追加。画像失敗は確定行動を巻き戻さない。 |
| 画像のキャンセル | `cancelled` を失敗コールバックで `failed` に上書きしていた点を修正。 |
| ブラウザの完成画像GET失敗・応答停止 | 同じ保存済み画像の取得を最大3回、各15秒で再試行。受信中も256 KiBを制限。401/403/404/410や型・サイズ不正は再試行しない。画面離脱で中止。画像生成APIは呼ばない。 |
| ブラウザの動画再生失敗 | 保存済み動画を読み直すボタンを追加。生成の再要求はしない。並行作業の結果画面コミットに取り込まれている。 |
| 伏線抽出の不正・時間切れ | 既存の元記録からの回復を維持。文章が失敗しても動画制作へ進む。 |
| 演出生成の失敗 | 30秒の呼び出し時間切れを `ENDING_CALL_TIMEOUT` として全体期限から分離。回復可能な失敗・文章用予算枯渇なら、確定状態だけから余韻の演出を作って続行。公開済み文章・タグを変更しない。 |
| 開始・終了フレームの生成・正規化失敗 | 各フレーム最大2回の予算内で再試行する。認証失敗・全体期限・キャンセル・予算枯渇は停止。 |
| 開始・終了フレームの検査不正・不明・通信失敗 | 同じ生成画像で再検査を優先し、解消せず生成枠が残れば修復する。明示的不合格も残り生成枠で修復。合格した画像だけを使用。明示的拒否は再試行しない。未完了なのにpassを含む応答も採用しない。 |
| 完成参照画像がゼロ | 最大30秒だけ既存画像を待ち、完成すれば制作へ進む。待機失敗やキャンセル後の遅着画像で制作を再開しない。古い画像でも終了時の確定状態を反映する。 |
| fal送信結果が曖昧・IDあり | 従来は失敗として中止処理へ進んでいた。同じIDを照会して結果回収を続けるよう修正。POSTは再送しない。 |
| fal送信結果が曖昧・IDなし | 回収対象を特定できない。再送せず未確認枠を維持する既存動作。 |
| fal状態照会の一時障害 | 既存の待機・再照会を維持。不正URL・リダイレクト・過大応答を繰り返し照会しないよう修正。 |
| fal結果GET・動画ダウンロード失敗 | 同じ要求の取得を最大3回に変更。短いバックオフとジョブ全体の期限で制限。 |
| 動画データの欠損 | MP4検証が失敗したら取得を再試行し、検証済み動画だけを保存。3回とも不正なら終了。 |
| 全体期限・結果失効・drain | 再試行中も停止。実行中の上流処理の停止未確認枠を維持。期限・予算を勝手に延長しない。 |
| キュー満杯・共有API予算枯渇・認証失敗 | 明示的な失敗。全体上限を増やして解決したことにはしない。演出を省略しても画像・検査・動画に必要な残予算は必要。 |
| メモリ容量・結果保持・サーバー再起動 | 既存の有限メモリ構成。再起動後の再開・永続ジョブは未実装で、別途構成変更が必要。 |

## ログ

- `request_failed`: `correlationId`、`route`、`method` を追加。`route` はサーバー定義だけを使用し、クエリや認証値を出さない。
- `scene_failed`: プレイID、段階、固定エラー分類。`SCENE_HTTP_*`、`SCENE_REQUEST_LIMIT`、`SCENE_TIMEOUT` 等。
- `scene_recovery`: 途中画像の回復開始。検査障害は同じ画像の再検査から進める。
- `ending_recovery`: 回復可能な失敗から回収を続けていることを示す。最終失敗ではない。
- `ending_failed_*`: 最終失敗。経過時間・残り時間を追加。既に存在していた伏線件数・バイト数・引用不一致件数も出力の許可項目へ追加。
