# Live会話の配送調査と修正（2026-09-15）

## 課題

ユーザー報告：アプリ版GPT-Liveに比べ会話がぎこちなく、発話が遅く感じられ、ノイズ感がある。他の試遊者から「別の指示があったので」という発言も報告された。これらを同一原因と断定せず、コードで確認できる指示混在と音声品質を分けて扱う。

## 確認できた経路

- セッション作成：hosted-runtime.ts → liveInstructions（live.ts）とgame-core.jsonの追加指示 → Live。
- 開始の呼びかけ：接続応答のopeningをPlayScreenが1.5秒後にdata channelへ送信。
- 本編：サーバーがoutboxへ事実・発話・回復指示・時間通知を積み、PlayScreenが500ms間隔のpoll後、同じdata channelへ送信。seqで重複送信を抑制する。
- 音声：ブラウザのマイク → WebRTC → Live → HTMLAudioElement。同一接続の音声を直接再生。アプリによるPCM再標本化、音声速度変更、複数TTSの混合は見当たらない。
- マイクはechoCancellation/noiseSuppressionを要求。実際に適用される処理は端末とブラウザ次第。実通信のジッター、音声補償、音響エコーは本調査では未計測。

指示の出所は複数あるが、独立した複数のLiveが同時に発話している証拠はない。通常のLive作成は前セッションの終了確認後に実行され、ブラウザも旧接続を閉じる。再接続中の実機競合まで確認したという意味ではない。

## コードで見つかった問題と対応

1. 行動後に結果・現況をthinkingで送り、同じ情報をcommentaryでも再送していた。結果と現況を一つの発話本文にまとめ、重複するthinkingを除いた。全ての本文は保持し、長い場合のみ上限内に分割する。
2. 物語段階更新後のcommentaryに「一言だけ自然に反応してから、次の現在状況を伝えて」という内部演出指示が混ざっていた。commentaryは結果と現況のみとし、物語方向は従来のthinkingとセッション指示で扱う。
3. 発話もUTF-8の480byte境界で無条件に分割しており、文の途中で切れていた。speechCommandsを分離し、上限に収まる文は分断しない。単独の文が上限を超える場合は従来どおり内容を欠落させず分割する。これは音声の途切れ改善の仮説であり、聴感改善は未測定。
4. 追加設定の「相談には答える」が、基本指示の「ゲーム相談は必ず委譲」と食い違っていた。日英とも委譲後の回答を自然に伝える方針へ統一。通常の会話テンポ、内部の指示や委譲を説明しないことも明示した。
5. 既存の開発用traceへlive_command_queued（時刻と通知種別だけ）を追加。本文、写真、認証情報は追加しない。

前提を維持：実行にはclient delegationが必要。サーバーだけが状態を確定。受付相づちの追加送信なし。終了時に次の状況を余分に話さない。この調査時点では時間警告と委譲回復のinstructions.appendを残した。時間警告はその後の[割り込み抑制の調整](time-warning-delivery.md)でthinking.appendへ変更した。

## 残る遅延要因と限界

- ゲーム質問はLive委譲後にResponsesの相談/意図判断を待ち、実行はさらに行動判断を待つ。一般会話と同じ応答時間とは限らない。
- コマンド取得は500msタイマーに加えてHTTP往復が必要。音声イベントのHTTP転送も順序を保って直列化しているため、多数の字幕断片や回線遅延による待ちがあり得る。並列化は証拠と委譲の順序を壊すため今回行わない。
- 発話速度を変える未確認APIパラメーターやplaybackRateは追加しない。マイクのエコー除去も安易に無効化しない。
- 「別の指示」発言の実録・ネットワーク統計は未取得。原因の確定、実音声の改善量、AWSでの改善は未確認。

## 手動確認

ローカルで既存のLive設定を使ってnpm run devを起動する。必要なら.env.localへENABLE_GAME_TRACE=1を設定し再起動する（productionでは無効）。同じPC・ブラウザ・マイク・回線で比較する。

1. 挨拶だけに自然に返答し、ゲーム相談では結果を待って回答すること。
2. 写真を送り「これで切って」と指示。相づちは一度、結果と次の状況がつながり、内部の「指示」「client」「サーバー」を読み上げないこと。
3. 長めの状況説明でも文の途中の不自然な停止が減るか確認すること。相談と実行で待ち時間を分けて記録する。
4. 残り1分通知のあと、勝手に実行したり以後ずっと急いだ口調になったりしないこと。
5. ノイズが残る場合は、同じPCでヘッドホン有無・別マイクを比較し、常時雑音か語尾の欠落かを区別する。WebRTC統計を採取する場合は接続先等を含むダンプを不用意に共有しない。

開発traceは同じプレイ所有者でGET /api/play/traceを参照。user_transcript_received → delegation_received → classification_started/decision_accepted → judgment_committed → live_command_queuedを比較できる。queuedは再生開始・再生完了ではない。traceはプレイ終了時に破棄するため、必要な計測は終了前に行う。

## 今回の検証結果

- npm.cmd test: 477/477成功（実API接続なし）。
- npm.cmd run build: 成功。
- 文境界の保持、長文の欠落防止、結果と現況の到達、演出指示の発話混入防止を回帰確認。
- 実Liveの発話速度・ノイズ・レイテンシーは未測定。マルチレビュー未実施。
