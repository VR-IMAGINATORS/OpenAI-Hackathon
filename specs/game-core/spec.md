# ゲームコアのブラッシュアップ

2026-09-15追記: [ゲームループハーネス改善仕様](../improve-game-loop-harness/spec.md)が、写真からの自律行動、結果確定前の訂正、知識分離、自然な通知・時間警告・再試行の要求を更新する。該当範囲では新仕様を優先する。新仕様の実装・自動検証を実施し、実音声の成立性は別途確認する。実績は[検証記録](../improve-game-loop-harness/verification.md)を参照。

Status: requirements approved in conversation (2026-09-13); implementation plan pending.

## 1. 目的・正本

写真と音声で工夫する本編において、状況を把握しやすくし、復唱・承認待ちによる停滞を減らす。ユーザー主導で相談・指示し、結果を音声・テキスト・画像で理解できるようにする。

根拠: proposal/game-core/game-core.md と2026-09-13のgrill-me Q1〜Q20および補足合意。本仕様はmobile-playtestの認識案確認・実行ボタン中心の操作と、hosted-multiplayerの本編UI・終了時の即時データ破棄のうち、以下で明示する部分を更新する。配信、認証、所有権、同時5プレイ、サーバー状態管理は引き継ぐ。

learning/の学習HTMLはローカル資料であり、仕様やAPI契約の正本ではない。疑似コードの関数・クラス構成は実装未確定。

## 2. スコープ

対象: 本編のメッセンジャー風UI、音声による自動実行、判定ハーネスの整理、部分進展と道具再利用、非同期の状況画像と表示前検査、日英対応、設定による調整。

対象外: 着信・応答演出など導入の再構築、本人の写真/名前/性別の収集、本人を使った画像、エンディング動画の新規実装、永続的な履歴保存、モデルの学習。既存の動画必須方針を撤回するものではない。言語選択は導入対象外の例外として開始前に追加する。

## 3. 画面・言語

- G01: モバイル主・PC副。相手のメッセージは左、自分は右、バブルの色を分ける。上端に小さな横長の通話状態インジケーターを置く。
- G01a（2026-09-14 UI相談で合意）: 本編上部は目標を上段、残り時間と写真送信回数を下段に常時表示する。日英の見出しは「現在の目標 / Current objective」「残り時間 / Time left」「残り送信回数 / Photo sends left」。シナリオの表示タイトルを解法を明かさない達成目標の文にし、目標20px・数字24px・ラベル14pxを基準にする。時間は分:秒（04:32等）。残り時間が1分以下になったとき赤と警告アイコンに変え、境目を越えた際に一度だけ短く拡大・発光する。再読み込み時の演出再生と連続点滅は行わず、動きを減らす設定では演出を省く。写真送信は残り2回でオレンジ、1回以下で赤と警告アイコン。詳細の開閉、長い目標の折り返し、チャットと撮影操作を維持する。
- G02: 下端の入力欄風領域はテキスト入力不可。左のカメラから撮影し、送信前は上部のサムネイルで確認、右端の送信ボタンで写真を送る。PCの画像選択を維持する。
- G03: 音声認識結果はユーザー側のメッセージとして表示する。AIが推測した道具用途や要約をユーザーが発言した内容として表示しない。相談も履歴に含む。遅れて届く文字起こしで履歴を更新できる。表示上の吹き出し境界と実行境界を同一視しない。
- G04: 結果テキストは音声で結果を伝えるタイミングで表示し、同じメッセージに画像の待機枠を用意する。厳密な音声再生時刻との同期保証は要求しない。画像到着を理由に音声で再説明しない。
- G05: 開始前に日本語/英語を選択。初期値はブラウザ言語によらず英語とし、言語選択UIでユーザーが変更できる（2026-09-14変更）。選択言語はプレイ中固定し、UI、AI音声、補足テキスト、エラーへ適用する。既存プレイの再読み込みでは、そのプレイの言語を復元する。音声認識結果は翻訳しない。

## 4. 会話・行動フロー

- G05a（2026-09-14 導入会話の調整）: 初回はAIが「聞こえる？ 聞こえたら返事をして」とだけ話して返事を待ち、ユーザーの返事後に「よかった、つながった」と自己紹介・舞台の状況・写真で協力する方法へ進む。日英で同じ順序にする。無音を返事とみなさず、相手が先に話せば呼びかけを重ねない。「聞こえない」「待って」には説明を止めて応じる。挨拶と接続確認だけの応答はLiveが扱い、ハーネスは追加の回答や攻略行動を発生させない。ゲームに関する質問・指示は通常どおり委譲する。再接続で導入を繰り返さない。開始ボタンは追加せず、時計開始と初回画像生成のタイミングは現行の接続完了時を維持する。

- G06（2026-09-15更新）: 写真は現在の障害に対する自明な用途の実行根拠となる。明らかな用途なら追加の指示を待たず行動し、不明な用途や具体的な危険だけ質問する。写真は有効な受信時に消費し、拒否や訂正でも返却しない。
- G07: 会話の区切りはGPT-Liveに任せる。ハーネスは履歴とゲーム状態から相談/実行指示/未取得・未完の発言を区別する。文字起こしの到着が一定時間止まったことだけで実行しない。Liveからの委譲通知も単独では実行許可とみなさない。
- G08: 「これで切れるかな？」などの相談では行動しない。「これで切って」「これでなんとかして」は実行指示として扱う。曖昧な指示も発言の範囲内で自然に解釈し、毎回正解になる補完はしない。無音、通信障害による発話未取得では行動を消費せず再発話を促せる。
- G09（2026-09-15更新）: サーバーの結果確定前に受信した中止・訂正は、判定中も独立した制御経路で分類する。未解決の制御入力がある間は古い結果を確定しない。確定後は巻き戻さない。自然言語の分類精度は日英の実会話で検証する。
- G10: 行動判定は1件ずつ。判定待ちも会話できるが、次の行動は実行しない。結果確定までは成否を断定しないようLiveへ指示する。モデルの発言はゲーム状態更新の根拠にしない。画像生成中は次の行動へ進める。
- G11: AIは困っている状況を説明し、基本はユーザー主導。助けを求められたときに段階的にヒントを出す。具体的な道具・解法の先回りを避ける。

### G05b（2026-09-15 導入の音声と補足チャットを分離）

- story付きシナリオの導入は追加AIを呼ばず、短い音声用原稿と表示専用の補足文をサーバーで組み立てる。音声は名乗り・一週間後の舞台・脱出の必要性・写真から道具を具現化してメイが扱えることに絞り、「時間がないから、詳しくはメッセージで送るわ」で終える。英語も同じ情報と順序にする。
- 補足文は一週間後から過去への通信、初期の公開済み状況・手がかり、写真と使用指示の依頼を含み、音声の後に独立した相手側の吹き出しへ一度だけ表示する。後続障害・未公開の真相・解法は含めない。Liveへの発話コマンドは作らず、自動読み上げ・復唱も指示で抑える。
- 表示時機は、実際のユーザー返事、メッセージへ引き継ぐ最後の案内の文字起こし、再生可能な出力音声の活動、その後の新しい静寂通知を組み合わせて推定する。既存の静寂検出は800ms連続サンプルを要する。無音や文字起こしの途絶だけで完了とせず、再生blocked・unknown・古い通知では表示しない。割り込み中は待機する。これはゲーム行動の確定条件には使わない。
- 再接続では導入音声を繰り返さない。導入中に切断した場合は、未表示の補足文を接続回復後に文章で一度届ける。音声が最後まで再生されたとは扱わない。表示済みの文は重複させない。
- 初回画像生成と時計開始は接続完了時のまま。初回画像の受信枠と完成画像は、音声では読まない補足文の吹き出しに添付する。「聞こえる？」の呼びかけには画像も受信枠も付けない。補足文の表示時に生成中ならその下に「未来から画像を受信中…」を表示し、完了後に同じ枠を画像へ置き換える。先に生成済みなら補足文と一緒に画像を表示する。補足文は発話後の会話順序で一度だけ現れ、再接続でも同じ画像との対応を保つ。補足文のための画像生成は追加しない。storyなしの旧V2設定は既存のopeningMessageを維持する。
- 実GPT-Liveの言い回しと再生終了の間合いは実音声で別途検証する。自動テストは模擬イベント・音声活動・HTTP配信の確認であり、実音声の成功とは扱わない。

## 5. ゲーム判定と状態

- G12: 指示の解釈→物理的な成立性と障害解決への十分性の判定→結果に沿う演出に分ける。通常の性質と状況に根拠があれば想定外の解法も認める。写真内の文字等に由来する魔法・特殊能力は付与しない。2026-09-15: 物性の制限は[無茶な工夫の許容](../creative-acceptance/spec.md)の範囲で拡張し、同一案の結果を維持する。
- G13: 完全に解決しなくても部分的な進展を保持し、後続の判定・会話・画像に反映する。効果がなければ変化なし。AIの即興で必ず進展させたり、解決不能な障害を追加したりしない。
- G14: 使用可能な道具は再撮影不要で音声指示によって再利用可能。行動回数の上限は設けず、写真送信0回でも継続できる。消費・破損などの状態に応じて利用可否を検証する。送信の計数と終了条件は [写真送信回数の制限](../photo-send-limit/spec.md) を正本とする。
- G15: 回数、在庫、進展、勝敗はサーバーが一度だけ確定。委譲/HTTPの再送、同じ指示への複数委譲、再接続で二重消費しない。モデル出力はschemaだけでなく、参照ID・現在状態・許可する遷移も検証する。
- G16: AI判定の技術的失敗と、ゲーム内の失敗を区別する。技術的失敗は行動を消費しない。確定済み結果の通知失敗では再実行/巻き戻しせず、同じ結果を再取得できる。
- G17: 既存のゲーム時計を維持。撮影・相談中は進行し、操作不能な判定待ち・接続復旧待ちは既存の上限内で停止。非同期の画像生成・検査だけでは時計を停止しない。Live/プレイの既存絶対期限は延長しない。

## 6. 非同期状況画像

- G18: 本編開始時と各行動結果の確定時に1枚ずつ生成する。失敗・変化なし・最後の成否も対象。相談や写真送信だけでは生成しない。最終行動の結果と勝敗確定が同じ場合は1枚とし、重複生成しない。エンディング動画とは別扱い。
- G19: 確定したゲーム状態から結果テキストと画像の入力を作る。画像生成側で新しい出来事、未入手の道具、未達成の攻略を追加しない。人物は差し替え可能な共通外見設定とし、顔が目立たない構図を基本にする。
- G20: 各画像は行動直後の状態スナップショットとメッセージIDに結び付ける。生成順が前後しても対応する過去の枠へ追加し、現在のゲーム状態を変更しない。過去の画像を最新状態versionとの不一致だけで棄却せず、元のプレイと結果メッセージの対応で検証する。再プレイの履歴に旧画像を混入させない。
- G21: 待機中は「未来から画像を受信中…」などの通信演出。APIで実進捗を取得できる場合のみ数値を表示し、取得不可なら数値なしのアニメーション。検査中・再試行中も待機表示を継続する。
- G22: 表示前に生成画像と確定状態を照合する。未入手の鍵、開いてはいけない扉、拘束状態など、攻略・状況理解に影響する大きな破綻を不合格とする。画風や細部の差は許容。検査不能・判断不能は公開しない。
- G23: 生成エラー、検査不合格、検査不能に対して自動再試行は最大1回、合計生成回数は最大2回。検査で分かった問題は再生成時の修正指示に使う。各画像ジョブに上限時間を持たせ、期限後の結果は表示しない。検査呼び出しにも試行上限を設ける。全体費用・同時実行上限も設計する。
- G24: 最終的な失敗表示は日本語で正確に「未来から画像の受信に失敗しました」。英語選択時は対応する英訳を用いる。画像失敗でゲームを止めず、確定済みテキストを残す。
- G25: ゲーム終了結果と通話終了を画像待ちで遅らせない。終了画面でチャットを閲覧し、期限内に完成した画像を受信できる。終了後の結果履歴と画像ジョブだけに有限の保持期限を設け、他人に公開しない。Liveの寿命と画像受信の寿命を分離する。保持方式と具体的期限は計画で決める。

## 7. 調整可能性・運用

- G26: 共通の会話/委譲ルールと、シナリオ固有の判定/描写/画像検査ルールをプランナーが設定ファイルで調整可能にする。相談・実行の例、ヒント段階、判定の厳しさ、許容する工夫、守るべき画像状態を含む。
- G27: 設定は検証後、新しく開始するプレイから適用。進行中のプレイへ途中反映しない。遅延画像ジョブも開始時に採用した設定を用いる。設定の読込・反映方式は計画で決める。
- G28: 開発中、入力に対する解釈と短い判定理由を追えるようにする。ただし、既存の写真・会話・プロンプト本文の本番ログ/永続保存禁止を自動解除しない。調整用の閲覧方法、権限と保持期限は計画で具体化する。
- G29: APIキー、生成画像、会話、状態は既存の所有権境界を守る。モデルや上流URLをブラウザが自由指定できる構成にしない。新しい画像処理にも要求サイズ・件数・期限・同時実行数を設定する。

## 8. 受け入れ条件

1. スマホで写真→自明な用途の自律実行→結果を通す。不明な用途は短い質問、相談・危険確認は必要に応じて挟み、確認ボタンや単なる復唱なしで一度だけ実行される。
2. 相談、用途を任せる発言、途中の間、音声未取得、遅い文字起こし、訂正を日英で試し、誤消費を記録する。
3. 未使用道具の再利用、部分進展の活用、使えない道具の拒否が、状態・音声・テキスト間で一致する。
4. 判定中も会話でき、次の行動が重複確定しない。終了・失効・操作権移動後の古い判定を反映しない。
5. 画像待ちでも先へ進め、逆順到着でも正しい結果メッセージへ画像を追加する。画像の検査前公開をしない。
6. 大きな画像矛盾/検査不能/生成失敗/timeoutを試し、生成最大2回と指定の失敗文言を確認する。細部の差で過剰に拒否しない。
7. 終了直前の画像も受信期限内で表示でき、期限・所有権・データ削除・有料接続終了を維持する。
8. UIとAIの日本語/英語を確認し、認識されたユーザー発言は翻訳・捏造しない。
9. 設定差し替えが新規プレイへ適用され、既存プレイの途中でルールが変わらない。
10. 自動テスト/模擬AI、実API、実スマホ、AWS同時5人、面白さの確認を区別して記録する。仕様作成時点では新機能の動作検証は未実施。

## 9. 計画で調査・確定する事項

- client delegationの文脈管理、遅延文字起こし、委譲漏れの回復、指示の同一性、訂正と実行予約の境界。学習HTMLの疑似コードで実現済みと扱わない。
- 画像生成/検査モデル、encoder-only方式を含む矛盾検出精度、日英での判定精度、API進捗の取得可否。
- 行動を伴わない時間切れ終了の画像は「最後の失敗も対象」という合意に沿って扱うが、接続失効・上限終了との区別とジョブ開始条件を計画で定義する。
- 画像の生成/検査/再試行の時間・料金・容量・同時実行上限と5人分の予算。終了後保持とサーバー再起動時の扱い。
- 設定schemaと読込方式、開発用判定トレースの閲覧方法、既存導入の文言を本編操作と矛盾させない最小の互換調整。

## 2026-09-14 承認済み追加: ハーネスの会話整合性と時間通知

ユーザーが調査後の対策方針と残り時間通知を承認。相談の分類理由と回答を分離し、公開状態に基づいて回答する。予約前の実行表明・確定前の成功表明をLiveへ禁止し、確定結果と現在の状況を分けて通知する。委譲の期限切れは再発話案内を返す。委譲漏れは未消費のユーザー発話を読み取り専用に分類し、明示指示に対してLiveへ再委譲を一度要求、解決しなければ再発話案内。無音だけで行動確定しない。世代・状態版・操作権・消費済み根拠を越えて実行しない。

2026-09-15の統合: 時間警告は[ハーネス改善H20〜H23](../improve-game-loop-harness/spec.md)の通常60秒・最終15秒の節目管理に従う。通常警告は音声活動が両側quietかつ再生可能なときthinking.appendの保留情報として一度だけ渡す。ユーザーの発言・考え中の間、自分の説明・回答を優先し、次の自然な切れ目で一度だけ穏やかに添える。通常警告は即時発話コマンドや結果の先頭へ変換しない。最終警告は最大3秒待機後にcommentaryで切替表現を送り、保留中の結果との結合も維持する。最終警告・終了結果が届いたら未発話の古い通常通知を取り消すよう指示する。設定はwarningsを正本とし、判定中/接続回復中の時計停止、警告期限、終了後の破棄を維持する。警告のチャット表示はLiveの字幕に一本化し、outbox発行時に固定文を追加しない。Liveが言い換えても同じ警告を二重表示しない。音量上の静寂は会話の完了を保証せず、Liveの切れ目判断・音声完了は実機確認として残す。時間切れ判定はサーバーが所有する。
