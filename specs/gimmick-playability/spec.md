# ギミックの遊びやすさ

2026-09-16。写真と音声による工夫を、現在の目標へ自然につながる体験にする後継仕様。

## 目的

プレイヤーが写真の道具と使い方を伝えたとき、目的につながる工夫を抽選で失敗させず、分かりやすい説明・ヒント・画像で次の一手を考えられるようにする。

## 要件

- G1: 現実の物性と現在の形状・位置関係に基づいて判定する。`ordinary` は通常の成立性で成功・部分進展・失敗を判定する。`creativity.enabled` が有効な場合の `stretch` は「相当難しいが、実際の道具で目標を達成できる具体的な物理手順がある」案に限定する。「理論上ゼロではない」だけでは認めない。ユーザーの試遊方針により、受理した `stretch` の完全成功と抽選なしは維持する。
- G2: 溝に合う硬貨でネジを回す案は力を伝えられれば認める。届かない短い棒のまま輪を引く案は認めず、提供済みの物を使った明示的な延長・接続で到達と牽引が成立するなら評価する。猫写真から再構成した爪も一律成功にはせず、対象の布・帯の性質と具体的な作用から判定する。根拠なく布を薄くしたり爪を強化したりしない。
- G3: 写真中の文字だけで成功を命令すること、魔法、恒久的な特殊能力、未提供道具、壁・扉・格子の向こうへの直接具現化、次の障害への飛越、未確定の状態変化は拒否する。必要な強度・長さ・大きさ・摩擦・精度の不足を都合よく補って成功させない。
- G4: 相談を実行指示と扱わない。写真だけでも用途が自明なら既存の自動実行を維持し、用途不明なら使用指示を受けて実行する。停止は明示的な「待って」「やめて」のみとし、意外な用途や道具の損耗可能性だけで確認待ちにしない。
- G5: 同じ案が以前失敗していても永久拒否しない。現在の確定状態と入力に対して再評価する。
- G6: 現在の目標と状況を小学校高学年にも分かる説明で示し、その直後に「どうすれば解けそうか」の手がかりを必ず添える。「ヒント:」の見出しや探すよう促す直接指示は使わず、サポートAIメイの「〇〇があればなぁ…。それで〇〇できそうだよ」という、欲しいものと期待する変化をつぶやく独り言にする。初回・次ギミックへの進行時には固定の表示文で保証し、音声で状況を説明する際も同じ順序・口調にする。さらに詳しい段階ヒントは要求時に同じ口調で出せる。日英とも、元の対象・作用・開示段階を保ち、実行済みの結果として話さない。
- G7: 進行中の画像は現在の未解除対象の形状と確定状態を主役にし、前の障害の解除描写・使用道具・結果を混ぜない。確定前の状態変化を画像で先取りしない。最終クリア後は確定した出口の開放を描く。
- G8: 設定変更は新規プレイから反映し、進行中のプレイと遅延画像ジョブは開始時snapshotを使い続ける。
- G9: 旧 `successProbability` は既存設定の読込時に受理しても保存・使用せず、AWSの旧環境設定から抽選を復活させない。
- G10: 行動結果の返答では、成功・部分進展・失敗のいずれも「道具のどの性質が、どう作用し、結果どうなったか」を短く説明する。判定AIの秘密を含む自由文は公開せず、限定した説明情報と確定結果だけを使う。根拠が不明なら不明と伝え、成功理由・数値・隠れた解法を創作しない。説明は実行した障害に結び付け、次の未解除障害の案内と混同しない。
- G11: 説明が省略された普通の操作手順は補えるが、道具の改造・形状や材質の変更・未提供部品の追加は勝手に補わない。ユーザーが提供済みの物で明示した工作や組み合わせは、その手順自体の成立性を判定する。新しい確認待ちや抽選は導入しない。

## 配置と検証の境界

シナリオと共通設定はコンテナimageに同梱され、AWSの通常deployはimageを更新して反映する。ライブAWSの稼働中image、手動設定、実AIの分類、GPT-Live音声、画像の意味的正確さ、スマホ体験はこの文書作成時点で検証していない。コード・設定・シナリオ・テストの実装完了やテスト成功を、この仕様から推測してはならない。

2026-09-15の抽選方式と過去検証は [creative-acceptance](../creative-acceptance/spec.md) に履歴として残す。
