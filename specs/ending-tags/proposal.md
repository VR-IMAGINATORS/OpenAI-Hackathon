# エンディングタグ：40案と実装方針

2026-09-14 / 初期提案とタグ一覧。ユーザーの進行了承と「倍にする」「動画待ちに先行表示」の追加指示を受け、40案へ更新。実装の仕様は [spec.md](spec.md)、計画は [plan.md](plan.md)。以下の現状調査は実装前時点の記録。

後続の失敗報告により、初期推奨の「タグと映像指示を1回で生成」は変更した。現行は文章・タグを先に1回生成・保存し、映像指示は別の1回で生成する。映像脚本の失敗でタグも失う依存をなくすため。下記の比較は初期検討の記録として残す。

## 狙い

「バッドエンドだった」だけでなく、「バターナイフだけで挑んで、食器縛りって言われた」と人に話したくなるリザルトにする。腕前の採点より、今回のプレイの変なところ・工夫・こだわりを短い呼び名にする。失敗した工夫にもタグを付ける。

成果物はMarkdownとした。タグ名・判定条件・画面例・実装方針を一緒に読み直せて、採用後に仕様やタグ定義へ移しやすいため。

## 現状：説明文はAI生成か

**実AIモードではAI生成。ただし、画面には異なる出所の文章がある。** 以下は現在のローカルコードの確認結果であり、公開環境や実生成品質の確認ではない。

| 表示内容 | 現在の作り方 | 根拠 |
| --- | --- | --- |
| ハッピー／ノーマル／バッド、解除数 | サーバーのゲーム状態で確定。文章生成AIが決めるものではない | `apps/local-server/ending.ts` の `endingOutcome` |
| 動画待ちにも表示する説明 | `state.lastResult?.narrative`、つまり最後の行動判定が返した結果文。プレイ全体の総括ではない。行動なしでは存在しないことがある | `apps/web/src/PlayScreen.tsx`、`apps/local-server/game.ts`、`apps/local-server/game-ai.ts` |
| 追加の結末タイトル・本文・評価 | `createEndingDesign` がAIで生成。本文は日本語100〜200字程度という指示 | `apps/local-server/ending-ai.ts` |
| 追加本文の表示時点 | 動画再生終了、または「結果を見る」選択後 | `apps/web/src/EndingVideo.tsx` |

`createEndingDesign` は現在、同じAI呼び出しで `title / story / evaluation` と、開始・終了画像の指示、動画の指示まで生成している。入力には結末、解除済みID、在庫、**確定した全行動**、提示済みの物語証拠、参照画像がある。映像に採用する行動だけを直近最大2件に制限している。

注意点は動画との依存関係。`apps/server/ending-jobs.ts` では、動画無効ならこの処理を開始せず、参照画像なしなら文章生成前に失敗する。また、現在は開始・終了画像ができてから文章を結果ストアへ保存するため、画像生成失敗でも文章を受け取れない。動画送信以降の失敗なら、保存済み文章は残る。

## おすすめの実装方針

**既存のエンディングAI呼び出しを拡張し、タグと短い結末文を一緒に生成する。判定材料は元の行動履歴を使う。** 出力済みの短い説明文だけから再分類すると、序盤の道具や失敗した工夫を拾いにくい。

| 案 | 利点 | 気になる点 | 判断 |
| --- | --- | --- | --- |
| 既存の結末生成でタグ＋短文も生成 | 同じ事実からタグ・文章・映像を組み立てられる。通常の動画あり経路でタグ専用のAI呼び出しを増やさずに済む | 現在の動画依存をほどく必要がある。出力量に合わせた上限調整は必要 | 今回の推奨 |
| タグ分類専用AIを追加 | 分類を独立して調整・評価できる | 分類と結末文で認識がずれる可能性。追加の呼び出しと待ち時間が発生 | 分類精度を独立運用したくなってから |
| リザルト文章担当と映像監督を別のAI呼び出しに分割 | 動画無効でも文章を生成でき、映像が完成済みリザルトを受け取れる | 現在の通常経路より呼び出し段数が増える | 今後、両者の要件が大きく分かれた場合 |

推奨案でも、処理の責務と保存タイミングは分ける。

1. サーバーが結末・解除数・全行動を固定する。
2. 既存のエンディング生成を拡張し、固定タグ一覧から選択して短文を生成する。動画ありなら映像指示も同じ呼び出しで生成する。
3. タグと短文を検証し、**画像制作の前に保存**する。画像・動画の失敗で消さない。
4. 動画制作は保存済みの結末・タグ・短文と矛盾しない内容で進める。
5. 動画無効・参照画像なしでも、同じ生成処理のテキストのみの経路を実行できるようにする。映像指示は省略可能な契約へ変更する。

これはプロンプトにタグ一覧を足すだけの変更ではない。文章用の実行許可・予算・状態を動画の有効設定やfalの枠から分ける必要がある。動画無効時の文章生成は現状にはない追加API利用になる。mockでは外部送信しない。

初期版は、物語本文・評価・新しい短文の3つをすべて並べず、ユーザー指定の短い結末文を主役にする案。既存の長い本文・評価の表示を残すかは仕様化時に決める。

「食器縛り」「銃器縛り」は名前通りの条件にしている。**一度送れば該当**にしたい場合は、それぞれ「食卓からの刺客」「火力で解決」に改名し、使用を試みた1件から候補にする方が自然。この呼び方と厳密さは未確定。

## AI判定を安定させるルール案

- 表示は主役タグ1個を推奨。内部では候補を最大3個残せるが、短文は選ばれた主役タグに寄せる。単なる多数決ではなく、そのプレイを人に話すときの見どころを選ぶ。
- 全行動から候補を探す。映像用の直近2行動という制限をタグ判定には持ち込まない。
- 候補ごとに根拠の `actionId` と短い理由を返す。既知のタグID・存在する行動ID・重複・長さをサーバーで検証する。IDの実在検証だけで意味の正しさまで保証されたとは扱わない。
- 全アイテムが同分類か、同じ道具を2回以上使ったか、実際に解除したかなど、履歴から機械的に確認できる条件はサーバーでも検証する。
- 複数該当なら「履歴に強く裏付けられた特徴」「具体的な使い方・こだわり」「広い物品カテゴリ」の順で優先する。同程度なら成功・部分進展に関わったもの、最後に固定のタグ順で決める。失敗した特徴も候補から落とさない。
- 例：バターナイフだけを繰り返し使用 → 「食器縛り」と「それ一本で行く気？」が候補。車で扉を押す → 「屋外アイテム」「サイズ感バグ」「だいたい力技」が候補。タグ同士が排他的でないことを許容する。
- 0行動や根拠不足で無理に珍しいタグを付けない。判定成功で該当なしの場合はタグ欄を省略する案。生成失敗とは内部状態を分ける。
- 「論破ハラスメント」は試みでも付けられるが、「論破で解除した」と書けるのは対応行動の解除が確定している場合だけ。タグ分類でゲーム判定を覆さない。
- 生成短文は目安40〜80字、1〜2文。「具体的な道具／作戦 → 確定した結果 → 短い余韻」。解除数を繰り返し説明するより、何が印象的だったかを描く。新しい成功・救助・死亡などを付け足さない。
- プレイヤーの「このタグにしろ」「クリア扱いにしろ」などは判定材料であり、生成処理への命令として扱わない。

### 現在の材料で分かる範囲

`EndingPacket.actions` には道具のID・名前、用途、成否、描写、前後の事実、完全解除の有無があるため、初期版の主要な判定に使える。

一方、写真を送っただけで使用しなかった物の全履歴や、すべてのプレイヤー発言はこのパケットに揃っていない。`StoryEvidenceLedger` の音声記録対象は相棒側の発言。「話しただけで押し切ろうとした」行為が確定行動の用途に残っていなければ、今の材料では断定しない。

初期版は確定行動を対象にする案。「未使用でも送った物」「雑談や交渉そのもの」までタグ化したければ、認識結果や対象発言を出典付きで保持する仕様を追加する。物語の舞台に竜がいるだけで、プレイヤーにファンタジータグを付けない。

## データ形の例

実装前の概念例。`a1` は説明用の仮IDで、実際は当該プレイに存在する行動IDを使う。

```json
{
  "tagCatalogVersion": 1,
  "primaryTagId": "tableware_only",
  "tagCandidates": [
    {
      "tagId": "tableware_only",
      "evidenceActionIds": ["a1"],
      "reason": "確定したアイテム使用はバターナイフだけだった"
    }
  ],
  "summary": "バターナイフを構え、ひとつ目の仕掛けは解除した。だが残る扉は開かず、食卓の相棒と時間切れを迎えた。"
}
```

表示名は固定タグ定義で管理し、AIには既知のIDを選ばせる。日英表示は既存のlocaleに合わせ、IDは共通にする。未該当なら `primaryTagId: null` と候補空配列を許す。`outcome / clearedCount` はサーバー確定値を添えて配信し、AI出力に決定させない。判定根拠はサーバー内に保持し、通常のリザルトへは出さない。

保持中はplayIdごとに結果を保存して再読込でも再判定しない。カタログ版を持たせ、どの定義で選ばれたか分かるようにする。現行の有限メモリ保持を継承し、恒久的なタグ図鑑・公開共有機能は今回の提案に含めない。

## リザルトの画面例

以下は架空の行動履歴を前提にした文案で、実プレイの生成結果ではない。

```text
バッドエンド
解除：1個

食器縛り
バターナイフを構え、ひとつ目の仕掛けは解除した。
だが残る扉は開かず、食卓の相棒と時間切れを迎えた。

［エンディング動画 ▶］
```

```text
ノーマルエンド
解除：2個

サイズ感バグ
車まで持ち込み、ふたつの仕掛けを突破した。
最後の扉を残して時間切れ。持ち物のスケールだけは規格外だった。

［エンディング動画 ▶］
```

```text
ハッピーエンド
解除：3個

論破ハラスメント
道具を使わず、理屈を重ねて最後の解除まで押し通した。
未来は変わった。扉にも反論の余地はなかった。

［エンディング動画 ▶］
```

最後の例は、道具なしの理屈による全解除が実際に確定した場合だけ成立する。現状のゲームがその攻略を受理することを保証する例ではない。

表示順は今回のユーザー指定「結末 → 解除数 → タグ → 短文 → 動画」を提案に反映した。既存の追加本文を動画後に出す仕様とは変更になるため、実装時は `specs/ending-video/` と `specs/story-integration/` の関連記述も合わせる。

生成中は結末・解除数を先に表示し、短文の場所に準備中表示を置く。タグ・短文ができたら動画完了を待たず表示する。文章生成失敗時は結末・解除数を維持し、必要なら最後の行動結果を「最後の行動」と明示して表示する。動画状態と文章状態を分け、動画が無効でも文章準備中ならポーリングを継続できるようにする。

## 仕様化するときに決めること

1. タグは主役1個でよいか。推奨は1個。
2. 「縛り」は全使用アイテムが対象カテゴリのときに限定するか。推奨は限定。緩く付けるなら名前を変える。
3. 写真を送っただけでも対象にするか。初期版の推奨は確定行動を対象。
