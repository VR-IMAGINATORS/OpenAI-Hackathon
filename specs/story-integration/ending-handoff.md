# 動画・リザルト担当への共有事項

2026-09-14。[本編の物語取り込み仕様](spec.md)から、別担当との接続に必要な点を抜粋する。担当への直接送信は行っていない。

同日追記：後続のユーザー指示により表示順を変更した。現行は結末・解除数→タグ・短文の自動先行表示→完成後の動画。以下の「動画後に本文表示」は当初の調整経緯として残す。現在の実装・確認には [ending-tags/spec.md](../ending-tags/spec.md) を使用する。

## 確定した要件

- 本編は会話版マスターv2の全6舞台・10障害・18構成へ拡張する。1プレイは3障害で、18構成からランダム選出する。
- 舞台の設定・初期の謎は引き継ぎ、展開と回収はプレイに応じてAIが生成する。結末を6種類の固定文から選ぶ形にはしない。
- 障害はモックの構成に揃える。既存Webの監禁犯への説得・陽動を最終障害として残さない。道具の自由な使い方・部分進展は維持する。
- 全解除3つでhappy、時間切れ・行動回数切れで2つならnormal、0〜1つならbad。継続不能な通信障害や手動終了は中断。部分進展を完全解除数へ加算しない。
- 通常終了の提示順は本編終了→動画→テキストのリザルト。エンド名・結末本文・評価は動画後に提示する。
- ゲーム時間は調整可能にする。現在の初期値は300秒だが、脚本・リザルトで「常に5分」と固定しない。

## 閲覧した別担当の計画との対応

参照: 別担当ブランチの `specs/ending-video/spec.md`、`plan.md`、`data-model.md`。調査開始時の文書はdraft表記。本メモ作成中に関連実装ファイルの追加を確認しており、共有型はまだ変更され得る。

結末分類、確定行動を優先すること、プレイ固有の結末生成、完全解除IDによるカウント、提示した伏線の保持は今回の合意と整合している。

### 1. 表示順を明確にしてほしい

E08とP4に「既存の結果を閲覧しながら動画の準備」「ゲーム結果はすぐ閲覧できる」という記述がある。提示済みの行動履歴と、新しいリザルトを分け、エンド名・追加の結末本文・評価は動画後に出す設計へ揃えてほしい。

APIやサーバー内部で結果を先に確定することは必要。UIがその値を動画前に結果発表として表示することとは区別する。既存の勝敗バッジ・音声通知・終了画面も、表示タイミングを確認する。

動画スキップ・失敗・機能無効時の表示は、この本編側の会話では未合意。別担当の会話で確定した例外があれば仕様へ明記し、通常の表示順と分けて扱ってほしい。

### 2. 6舞台の状態を受け取れるようにしてほしい

現在の倉庫の `wrists / door / escape` の3キーだけを必須にせず、選ばれた舞台・障害が宣言するfactsと未解除の機構を使う。目隠し、足首の拘束、曇った窓、シャッターなども対象になる。

同じ解除数でも身体の状態と未達成の障害は異なる。normalだから必ず歩ける、badだから必ず手首が縛られている、と固定せず、そのプレイの確定状態を根拠にする。

### 3. P1の共通部品を二重に作らない

別担当のP1では以下を扱うため、本編取り込み側では同じ仕組みを別名で増やさず、共通化する方針。

- 完全解除ID・終了理由・確定行動履歴とエンド種別の決定。
- `StoryEvidenceLedger` による、序盤からの提示済み描写・伏線の保持。
- `EndingPacket` による、確定状態と生成材料の引き渡し。

本編側は舞台抽選、共通世界設定、導入・中盤・終盤の語り、障害の物理条件・部分進展、時間設定を担当する。エンディング本文・評価・脚本の生成と動画・リザルト表示は別担当にまとめる分担案。

## 合わせたいデータ契約

以下は必要な情報の一覧であり、新しい型名・APIを確定したものではない。既存のEndingPacket案へ反映する形を優先する。

| 情報 | 本編側での意味 | エンディング側での用途 |
| --- | --- | --- |
| playId、設定snapshotの識別子、言語 | 開始時に採用した一つのプレイ | 再抽選・別プレイの混入を防ぐ |
| 舞台ID、障害順、場所・人物・空間の設定 | 選出された舞台の背景 | 倉庫固定の脚本・構図を避ける |
| 実際に提示した描写・伏線とsourceId | 設定にあるだけの未提示情報とは別 | 序盤を含めた伏線の回収 |
| 全行動のID・障害ID・用途・道具・前後のfacts・成否 | コードが確定した履歴 | プレイヤーの工夫を反映し、直近最大2行動を映像の候補にする |
| 完全解除ID・残る障害と機構・最終facts・在庫状態 | 最終状態の根拠 | 部分進展を保ち、未脱出なのに出口を越えるなどの矛盾を避ける |
| 終了理由・確定エンド種別・使用回数・採用した時間設定 | 生成AIが再判定しない値 | 結果分類、0行動終了、中断の扱い |
| 画像のmessageId・gameVersion・取得状態 | その状態に対応する検査済み画像への参照 | 後着・失敗・初期画像のみのケースを区別する |

提示済みの語りも、物理的な確定状態より優先しない。未公開のmysteryや後続障害を、すでに提示した伏線として扱わない。画像は完成した順番だけで最新と決めない。

## 統合時の確認

- 本編の導入・進行描写をStoryEvidenceLedgerへ登録する方法と、実際の画面表示・音声文字起こしとの対応。
- `game.ts`、`hosted-runtime.ts`、共有型の変更の担当と統合順。本編取り込みでは、P1で実装された共通の終了判定・材料保持を使う。
- 同じ舞台・同じ種別で、伏線と使った物が異なるプレイを渡し、生成入力がそのプレイに対応すること。
- 最後の許可行動での成功、0行動の時間切れ、部分進展を残したnormal/bad、通常終了後の通話切断を正しく扱えること。
- 日英のリザルトと、本編終了→動画→リザルトの順。動画の実生成品質は別に確認する。

## 本編側の実装済み接点（2026-09-14）

本編は `codex/story-integration`、動画側は元の作業フォルダの `codex/web-ending-video` で別々に作業した。動画側の未コミット変更は本編ブランチへ取り込んでいない。統合後の連携テストは未実施。

- `ScenarioSnapshot.scenarioV2` は選出済みの3障害と物語を保持する。`id` は元舞台ID＋構成番号、各 `obstacles[].id` は元マスターのギミックID。倉庫の3キーを前提にしない。
- `scenarioV2.story` は `aiName / world / mystery / openingClue / phases` の日英設定。設定そのものは提示済みの証拠ではない。
- `storyOpening()` の舞台・初期手掛かりを含む本文を `GameRuntime.presentScene()` へ渡す。動画側の `recordSceneEvidence()` をこの経路に残せば、実際の初回表示を台帳へ保持できる。Liveが話した展開は既存のassistant transcript経路で記録する。
- `storyNarration()` はLiveへ渡す演出指示。これをそのままStoryEvidenceLedgerへ登録しない。終わりの回収には実際に提示した本文・音声文字起こしを使う。
- `obstacles[].completionFact` は `{ key: 元ギミックID, value: "cleared" }`。factsは `blocked / partial / cleared`。本編の `game.ts` は `success` と完了factの一致を、状態・在庫・回数の変更前に検査する。動画側の解除ID・確定行動・終了理由の記録も残す。
- 未解除の機構は `snapshot.scenarioV2.obstacles[].mechanism[locale]`、部分進展の具体的な内容は確定situation・行動履歴を併用する。`partial` だけから具体的な身体状態を推測しない。
- 時間は `snapshot.scenarioV2.rules.totalTimeSeconds` を使う。カタログの既定は300秒だが変更可能。動画・結果本文で5分と固定しない。

統合で重なり得る主なファイルは `game.ts`、`hosted-runtime.ts`、`apps/server/app.ts`・`config.ts`、`.env.local.example`、`docs/development.md`。本編の抽選・物語・完了fact検査と、動画側の終了材料保持・表示順の双方を残す。
