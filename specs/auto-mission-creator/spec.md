# 自動ミッション生成・成立性評価プロトタイプ

Status: requirements approved in conversation (2026-09-14); implementation plan approved (2026-09-14).

## 1. 目的と根拠

AI自身が新しいギミック、達成条件、ギミック同士のつながりを考え、遠隔脱出ゲームとして成立するストーリーを生成する。その生成案に対する評価器を構築し、人間が最終案と評価根拠をテキストで確認できるところまでを今回の成果物とする。

根拠は[企画資料](../../proposal/auto-mission-creator/auto-mission-creator.md)と、2026-09-14のgrill-me Q1〜Q17およびまとめへのユーザー承認。判断の理由は[設計判断](../../.specworkflow/discussions/2026-09-14-auto-mission-creator.md)に記録する。資料にあるハッカソン主催者の意図や複数モデルの優位性は企画上の仮説であり、本仕様の検証済み事実とは扱わない。

合格とは、固定条件に対する必須検査がすべて完了し、重大な問題と成立に必要な説明不足が解消していることを意味する。LLMの合格を物理的成立性の数学的証明や、面白さの保証と呼ばない。

## 2. スコープ

### 対象

- 設定ファイルを入力とするCLIによる、コントラクト生成・検証、ストーリー生成、機械検査、独立AI評価、指摘検証、修正。
- 1実行につき1案。初回評価後の修正は最大2回。別案の生成は別実行。
- 一本道の複数ギミックと、その間の道具・状況の引き継ぎ。
- ダークテーマのHTMLレポートと再検証用JSONの保存。
- 正常例と意図的な不成立例を使った評価器の検証。

### 今回の対象外

- Webゲームへの組み込み、リアルタイムのシナリオ変更、AWSへの配置。
- 分岐するストーリー、面白さの採点、画像・動画生成、画像検索。
- ファンタジーや特殊能力の導入、モデルの学習。
- 人間の承認待ちを含む生成処理、失敗後に自動で別案を作り続ける処理。
- 生成物の合格を理由とした本番シナリオの自動更新。

開発時のマルチレビューはユーザーの指示まで省略する。一方、機能として実装する複数視点のストーリー評価は明示的に承認された要件であり、省略しない。この二つは別の運用である。

## 3. 入力・固定条件

- AMC-01: 世界観は「未来の自分を、写真から具現化する道具と使用指示で助ける」。特殊能力を付与せず、都合のよい道具や能力を後から追加しない。
- AMC-02: 世界観、許容する道具、物理的制約は設定として分離する。今回の道具基準はプランナーが編集できる身近な物のリスト。ドラゴン等の別世界観は将来差し替える余地を残すが、今回の成立性検証には含めない。
- AMC-03: 送信回数、写真枚数、行動回数、時間等のゲームルールは外から与えた難易度設定を使う。数値をプロンプトや検査コードへ固定しない。並行開発中の難易度UIとの統合は今回行わない。
- AMC-04: 既存のプランナー案は参考例として渡す。既存ギミックの選択・並べ替えだけを生成機能の達成とは扱わない。
- AMC-05: 入力設定、使用した参考例、モデル設定を実行単位で保存し、実行中の設定編集によりその試行の条件が変わらないようにする。

## 4. コントラクト

- AMC-06: 外から与えた世界観・難易度・道具制約の下で、ギミックの達成条件と全体の流れ、脱出までの成立条件をコントラクトとして生成し、整合性を検証する。
- AMC-07: 検証済みコントラクトを固定してからストーリー本文・解法手順を生成する。外部条件はコントラクト生成時にも変更不可。固定後のコントラクトは修正担当も検証役も変更できない。
- AMC-08: コントラクト自体の矛盾、未検証、外部条件違反はその試行の失敗とする。回数を増やす、達成条件を弱める、拘束をなくす等で合格条件をすり替えない。固定版と候補が参照する版の一致を検査する。

## 5. ストーリー・解法データ

- AMC-09: プレイヤー向けの状況説明、各ギミックの達成条件、次のギミックへ進む理由、最終的な脱出状態を記述する。
- AMC-10: 各ギミックに具体的な解法例を持たせる。身近な物のリスト内の道具を使い、開始から脱出まで設定回数内で到達する一連の手順を少なくとも一つ示す。
- AMC-11: 解法例は成立性を示すための資料であり、唯一の正解リストではない。リスト外の道具を含む別解を将来のプレイ時に許容する方針を維持する。別解の実行判定は本プロトタイプの対象外。
- AMC-12: 各手順には、前提条件、使用する道具、道具の取得・具現化に必要な送信、行動等の消費、実行後の状態を構造化して持たせる。
- AMC-13: 道具は所在、状態、再利用可能性を追跡する。「手元にある」「設置している」「失われた・使い切った」を基本とし、次の場所へ持ち運べる根拠や回収動作を明示する。回収・持ち運びに必要な動作も行動回数の検査対象にする。
- AMC-14: ギミック間の状態・道具の連続性を維持する。拘束中に何ができるか、どこに道具が具現化するかなど、解法の成立に必要な配置・身体動作を説明する。不明な情報を評価者が都合よく補完して合格にしない。

## 6. 評価の構成

### 機械検査

- AMC-15: 形式、参照先、前提条件、道具の所在・消費・再利用、状態遷移、回数の合計、最終到達条件をコードで順に検査する。無効な参照や矛盾をAIの高評価で打ち消さない。
- AMC-16: 機械検査の成功は、記述された手順が形式上成立することを示す。実際の身体動作・物理的妥当性や自然文と構造化データの一致まで証明したとは扱わない。

### 独立評価

- AMC-17: 同じ固定コントラクトと同じ版の生成案を、以下の3視点で独立評価する。
  1. 身体動作・物理的成立性。
  2. 道具の入手・消費、制限回数。
  3. ストーリーの因果関係、状態の連続性、成立に必要な説明の不足。
- AMC-18: 評価者は他者の評価結果を見ない。修正後も過去の合否や指摘履歴を見せず、修正案そのものを評価する。修正担当と指摘の検証役は必要な履歴を参照できる。
- AMC-19: 指摘は対象箇所、成立しない理由、不足している情報を示す。単なる印象や面白さは今回の合否に入れない。

### 指摘検証・合否

- AMC-20: 生成担当とは別の検証役が指摘の妥当性を確認する。棄却には、当該案・コントラクト等の根拠に基づく反証を必要とする。別のモデルが合格と言っただけでは反証にならない。
- AMC-21: 妥当な重大指摘と成立に必要な説明不足は修正対象。裏付けのない棄却、解消できない不一致、必要な評価の欠落を残したまま合格にしない。平均点・多数決で重大指摘を相殺しない。
- AMC-22: 修正後は機械検査と独立評価を再実行する。修正箇所以外にも影響が出るため、全体の脱出手順を検査する。
- AMC-23: 機械検査を含むすべての必須検査が完了し、妥当な重大指摘・説明不足・未解決の不一致がなければ合格。それ以外は修正または最終失敗。人間の承認待ち状態は設けない。

## 7. 実行制御とエラー

- AMC-24: 通常のOpenAI API経由で実行し、運営が管理する資格情報をローカル実行環境から取得する。ルートの私有.envは使用せず、既存プロジェクトの秘密情報管理方針に従う。
- AMC-25: コントラクト・ストーリーの生成と修正はAstraなどの最上位モデルが担当する（2026-09-14追加指示）。下位モデルへの自動フォールバックは禁止。生成担当、3視点の評価者、検証役のモデルと指示を設定から選べる。資料のSol/Terra/Luna等はAPI利用可能性を確認する前に有効なモデルIDとして固定しない。モデル・役割・使用量・所要時間を記録する。
- AMC-26: ユーザー入力後2〜3分を目標とし、初回は全体10分（600秒）のタイムアウトで実測する（2026-09-14追加合意）。生成・各評価・指摘検証・修正の段階別時間と全体の実経過時間を記録する。API呼び出し回数、出力トークン数、全体の実行時間に設定可能な上限を設ける。修正上限と独立して守り、並行評価や再試行によって上限を迂回しない。
- AMC-27: 必要な評価がAPIエラーやタイムアウトで完了しなければ最終結果は失敗。成功済みの評価者だけで合格しない。通信エラーはストーリー欠陥と区別し、物語の修正材料にしない。一時的な再試行を設ける場合も上限内とし、具体的な回数は計画で定める。
- AMC-28: 修正上限、予算上限、未解決指摘、無効な構造化出力等で終了した場合、終了理由と途中成果を保存する。最終案が存在しない段階の失敗では、存在するかのようにストーリーを補わない。
- AMC-29: 生成文・参考資料・評価出力はデータとして扱い、固定条件や評価手順を変更する命令として実行しない。HTMLでは生成文を安全に表示し、資格情報をHTML/JSONやログに含めない。

## 8. CLI・レポート

- AMC-30: CLIで設定を指定して生成・評価し、1実行ごとに独立した結果を保存する。正常に完了した実行と失敗を呼び出し元が区別できる。
- AMC-31: ダークテーマHTMLには、合否、固定条件、最終ストーリー、解法手順、道具と状態の推移、各評価、指摘と検証役の反証、修正履歴、使用モデル・使用量・時間を表示する。
- AMC-32: 失敗時は「生成できませんでした」と理由を表示し、作成済みの最終案は不合格・未検証等の状態を明示して表示する。途中失敗の場合も得られた評価を確認できる。合格案と取り違えない。
- AMC-33: JSONには入力スナップショット、固定コントラクト、各版の生成案、機械検査・独立評価・指摘検証の結果、修正履歴、実行メタデータを保存する。保存した案を評価器へ再入力できる。再評価は新しい結果として保存し、過去の判定を上書きしない。LLMの出力が再実行で完全一致することは要求しない。

## 9. 評価器の検証と受け入れ条件

- AMC-34: 正常例に加え、少なくとも「行動回数不足」「前段で使い切った道具の再利用」「拘束で解法動作が不可能」の既知不成立例を用意する。成立に必要な情報不足も検証対象にする。
- AMC-35: 期待する判定と問題箇所をケース側に保持し、評価者には正解ラベルを見せず評価する。レポートで期待判定と実判定、検出根拠を比較できる。誤合格と誤不合格の双方を残す。
- AMC-36: 自動テストでは予算・修正上限、固定条件の不変性、必須評価欠落、重大指摘の棄却条件、相互非公開、道具/回数/状態検査、失敗時保存を検証する。
- AMC-37: 実APIで生成・評価した結果と模擬APIの検証を区別する。既知ケースで問題を検出できても、任意の生成案に対する完全な精度を達成したとは扱わない。

| 受け入れ観点   | 確認内容                                                             |
| -------------- | -------------------------------------------------------------------- |
| 新しいギミック | 参考例の選択だけではない生成案と、その達成条件・成立手順が保存される |
| 固定条件       | 生成・修正・検証を通して外部条件と固定コントラクトが変わらない       |
| 解法の成立     | リスト内の道具で制限回数内に脱出する手順を機械・AIの両方で検査する   |
| 評価の独立性   | 3視点が互いの判定を見ず評価し、検証役が根拠付きで指摘を扱う          |
| 終了の確実性   | 1案・最大2回修正・実行上限を守り、評価欠落や未解決を合格しない       |
| 結果の確認     | 合格/失敗ともHTMLとJSONで最終案・根拠・履歴を確認できる              |
| 評価器の検証   | 正常例・既知不成立例の期待判定と実判定を比較できる                   |

## 10. 計画フェーズで具体化する事項

要件の再ヒアリングではなく、実装計画で調査・設計する事項として残す。

- APIで利用可能な具体的モデルID、役割への割り当て、出力形式、単価・待ち時間を踏まえた上限の初期値。
- 固定コントラクトの検証手順、指摘検証の出力契約、コードが扱う合否・エラーの型。
- 難易度設定の入力形式と、1行動/送信/回収・持ち運びの数え方の具体化。動作を一つの文章へまとめて回数を過少計上できない検査方法。
- 時間制限への適合をどこまで検査するか。手順の存在だけでは実際のプレイ時間内の完了を保証できない点を明示する。
- CLI名、保存先、プロトタイプの出力言語、ギミック数と道具リストの初期値、既知ケースの件数。
- 既存scenario v2やeval-workflowから再利用するものと、独立プロトタイプの境界。現行ゲームでそのまま読み込める互換性は未確定。

## 11. 将来の拡張

ゲームへ組み込む際は、生成が失敗し続けた場合に保存済みの合格ストーリーへフォールバックする。現在の世界観・難易度に適合する候補の選択や保存管理は、その段階で設計する。面白さの評価、画像検索・生成、ファンタジー設定は別の機能として扱う。
