# 自然な会話と自律行動を支えるゲームループハーネス

Status: 2026-09-15のgrill-meと最終まとめで要件承認済み。仕様化済み。計画・実装・新要件の動作検証は未実施。

## 1. 目的と正本

未来の相棒が状況を理解して行動し、プレイヤーが自然に助けられる体験を作る。不要な用途確認、内部処理の読み上げ、依頼の取りこぼし、時間警告による唐突な発話切断を減らす。「通信の向こう側に人間がいるかのような体験」を目指すが、相棒がAIである世界設定は維持する。

根拠: [企画資料](../../proposal/improve-game-loop-harness/improve-game-loop-harness.md)、[判断記録](../../.specworkflow/discussions/2026-09-15-improve-game-loop-harness.md)。本書は変更する要求の正本であり、現状の実装説明ではない。

| 既存仕様 | 今回優先する変更 |
| --- | --- |
| game-core G06〜G08 | 用途が自明な写真を実行根拠にできる。用途質問を必須としない。相談・未完の発話だけで実行しない原則は維持 |
| game-core G09 | 訂正可能な境界を受付時から結果確定前へ変更 |
| game-core G11/G12/G26 | 自律行動、柔軟性、知識分離、プランナー設定を具体化 |
| game-core G16とエラー通知 | 一度の自動再試行と状態確認、メタ的な定型文の見直し |
| game-coreの2026-09-14時間通知追記 | 即時差し込みから会話を考慮した警告へ変更 |
| story-integrationの語り | 未開示情報をLiveへ渡さない知識境界を追加。舞台・障害構成は維持 |

上記以外の[game-core](../game-core/spec.md)、[写真送信制限](../photo-send-limit/spec.md)、[シナリオ](../story-integration/spec.md)、[難易度](../difficulty-selection/spec.md)、[公開構成](../hosted-multiplayer/spec.md)を引き継ぐ。

## 2. スコープとUI

- 対象: 既存シナリオの知識整理、許容方針、Liveへの指示と情報、意図判断、自律行動、訂正、復旧、音声警告。モバイル主・PC副、日英の既存対応を維持する。
- メッセンジャーUI、導入動画→着信→応答、写真送信、ユーザー自身の音声文字起こし、確定結果と非同期画像を維持する。用途確認・実行の新しいボタンを追加しない。
- UIの正確な残り時間・送信数表示は維持する。自然な会話のために画面から数値を隠す変更ではない。
- 対象外: クレジット制、自動ミッション生成器との接続、新世界観や完成脚本の大量作成、エンディング刷新、AWSリリース、永続履歴、GPT-Liveから別方式への置換。

## 3. 自律行動

- H01: 写真を受信・認識したとき、現在の依頼・状況・ユーザーの訂正を踏まえ、用途が自明なら追加質問をせず行動へ進む。写真送信を実行根拠として扱う。例えば切る物を求めた後のハサミはすぐ使う。
- H02: 用途が不明なら短い質問を返す。複数案でも現在の目標に明確に沿い、不必要なリスクや消費が少ない案なら自律選択できる。結果やリスクが大きく異なる選択は確認する。
- H03: 現在の目標に必要な自然な下位手順を補完する。世界設定で可能な主体・既存の道具・設備・範囲だけで行う。必要な道具や能力を創作せず、相棒に身体がないなどの制約を無断で変更しない。
- H04: 現在の障害を越えたら必要な観察・報告まで行い、次の障害の攻略はユーザーに判断を返す。自律的な全問連続攻略は行わない。状況把握に必要な自然な移動等は世界設定上可能な範囲で含められる。
- H05: 低リスクの試行は成功が確実でなくても実行できる。道具喪失や不可逆な悪化が予測され、未承認なら具体的なリスクを短く伝えて確認する。「いいからやって」は可能な危険行動の試行許可であり、不可能な行動や成功の強制を認める指示ではない。
- H06: 音声の相談だけでは実行しない。用途を任せる依頼は実行可能。写真起点の自律行動と同じ音声指示が重なっても一つの行動として扱う。ユーザーの保留・中止を写真到着で無視しない。
- H07: 行動は一件ずつ確定する。結果確定前の中止・訂正は反映し、古い判定を状態・発話・画像に反映しない。確定後なら結果を巻き戻さず、起きたことを伝えて次の対応へ進む。モデルの成功発言は確定の根拠にしない。

## 4. 世界観に沿う柔軟性

- H08: 許容方針をプランナーが自然文で変更できる。「日常離れした溶岩などは拒否」「コメディ調で物理法則に反しなければ許容」等を表現できる。品目の固定リストだけに依存しない。
- H09: 写真からの具現化、通常の物性、扱える主体、接触・位置関係・周囲への影響を判断する。物理的な因果を守り、写真内の文字やユーザーの押し切りで特殊能力を付与しない。想定解の道具名との不一致だけでは拒否しない。
- H10: 方針と状況に基づく判断と根拠をプレイ内で維持する。誤認識訂正・新情報があれば見直せる。同じ情報なのに毎回別の世界ルールにしない。
- H11: 拒否時は既存設定に根拠を置いた短い説明と、役立つ性質を伝える。新しい重量上限・電池・通信事情等を創作せず、別の物へ黙って変換しない。設定上説明できなければ「こちらでは道具にできそうにない」等に留める。
- H12: 有効な写真の受信時に送信数を消費し、認識後の拒否でも返却しない。同一送信の再処理・再試行では重複消費しない。現行では行動や会話自体に送信数を課さず、行動上限を再導入しない。運用API上限は維持する。

## 5. 知識・観察・回答

- H13: シナリオ情報を「相棒が既に知っている事実」「現在観察可能な手掛かり」「未開示の情報」に分離する。Liveには既知・開示済み情報だけを渡す。秘密を渡して口止めする方式は不可。
- H14: 進行条件成立時の自動開示と、ユーザーの質問・調査依頼に応じた開示を扱う。バックエンドが状態と要求に照らして開示可能な情報を選び、ハーネスが許可した情報だけをLiveへ返す。未開示の正解・犯人情報を質問だけで一括提供しない。
- H15: その場で見聞きする無害な観察は、回答に必要なら自律的に行う。扉を開ける・物を動かす等は通常の状態変更・リスク判断に従う。取得できない事実は不明と答え、即興の手掛かりを事実にしない。
- H16: 推測は支持する既知・観察情報と区別して保持し、不確かな表現で伝える。複数の足音から複数人を疑う等は可能。新情報で訂正し、繰り返し発言したことだけで確定へ昇格しない。
- H17: 障害解決後は、新しい状況と困りごとを自発的に伝える。解き方・具体的な道具の提案は相談されたときに行う。導入チュートリアルの遊び方説明は例外とする。

## 6. 発話と時間警告

- H18: Liveの指示、バックエンドが作る回答、固定の通知文を通して、内部処理・委譲・消費判定を台詞に持ち込まない。「別の指示が来た」「行動は消費していません」等を通常の応答として出さない。実行開始・確認中・確定結果を混同しない。
- H19: 残り送信数は自発的に繰り返さず、質問された場合と使い切った場合に伝える。自然な表現を優先するが、明示的な数値の質問には正確に答える。設定にない電池や通信制約で説明しない。
- H20: 残り時間は設定した節目で警告する。通常の警告はユーザー・相棒の会話の切れ目を待つ。最終警告だけは有限の待機上限を持ち、終了前の通知機会を確保する。
- H21: 最終警告も可能な限り短い発話の区切りを使い、「あっ、まずい！ もう時間がない！」等、相棒が気づいて話を切り替える表現にする。音声を切断して別の定型文を流す体験を避ける。APIの制御範囲と実際の聞こえ方は計画・実機検証で確認する。
- H22: 時計と終了条件はサーバーが所有する。警告待ちや警告発話だけでは時計を止めず、既存の判定・接続復旧時の停止規則を維持する。終了後に古い警告を流さず、遅れた警告で誤った残り時間を断定しない。
- H23: 節目、通常/最終の扱い、最終警告の待機上限、日英の表現・口調を設定可能にする。具体形式と初期秒数は計画で決める。未確認のAPIイベントを仮定しない。

## 7. 状態・エラー・設定

- H24: 行動の技術的失敗への自動再試行は元の試行に加えて一度まで。結果不明なら先に状態を確認し、確定済みなら同じ結果を再通知する。確定の有無を解決できない状態で別行動として再実行しない。上流通信の内部再試行と合わせた上限を設計する。
- H25: 復旧できなければ、結果を捏造せず状態に合う短い案内を返す。処理を終えているのに「少し待って」で永遠に待たせない。ゲーム内で試行が失敗した結果を技術的失敗として自動再実行しない。
- H26: 写真、音声根拠、行動、状態版、訂正、開示情報、推測、結果、通知の対応を管理し、再送・競合・再接続でも一度だけ確定する。存在しないdelegation IDを作らず、写真起点の実行と実際のLive委譲応答を区別する。
- H27: 確定結果と状況画像の対応を維持する。取り消し済みの判定で画像を生成・公開しない。会話や知識開示だけのために新しい画像生成を必須化しない。
- H28: 既存シナリオ群に適用し、舞台・障害・世界設定を整合させる。未知の犯人情報や完成脚本を埋めるために創作しない。開示条件の検証用データは製品シナリオと区別する。
- H29: 設定は検証して新規プレイから適用し、進行中は開始時の設定を維持する。秘密をブラウザの一般公開状態やLiveの指示・回答へ漏らさない。認証・所有権・上限・ログ禁止を維持する。

## 8. 受け入れ条件

| ID | 場面 | 期待する結果 |
| --- | --- | --- |
| A01 | 切る物を求められてハサミを送信 | 用途質問なしで一度行動し、確定結果と画像へ進む |
| A02 | 用途不明の写真、結果が大きく異なる使い方 | 必要な質問だけを返し、勝手に選択しない |
| A03 | 写真の自律実行と同じ音声指示が重なる | 二重実行・二重送信消費がない |
| A04 | 一つの障害を解決 | 新しい状況を伝え、次の障害を勝手に解かず、解法を先回りしない |
| A05 | 軽い試行と道具喪失の危険がある試行 | 前者は自律、後者は未承認なら確認。承認後も物理制約を守る |
| A06 | 同じ物を異なる自然文方針で評価 | 方針による許容差を評価でき、同一プレイで理由なく判断が反転しない |
| A07 | 方針上拒否される写真 | 送信数は返さず、設定を創作せず説明する |
| A08 | 隠された情報について質問 | 開示条件成立前はLive入力に秘密を含めず、不明または根拠付き推測。条件成立・適切な調査後のみ開示 |
| A09 | 推測に反する新しい観察 | 推測を訂正し、真相や過去状態を都合よく書き換えない |
| A10 | 結果確定前/後に「待って」「そっちじゃない」 | 前は中止・変更、後は巻き戻さず説明。古い結果・画像の混入なし |
| A11 | 行動の処理失敗、結果通知だけの失敗 | 再試行は一度、確定結果は再利用、二重実行なし。復旧失敗時も応答がある |
| A12 | 相棒またはユーザーが話しているときの時間警告 | 通常は区切り待ち。最終は有限待機と自然な切り替えを実音声で確認 |
| A13 | 警告保留中に時間切れ・終了 | 終了を遅らせず、終了後の古い警告がない |
| A14 | 残り回数を聞く/聞かない/使い切る | 必要時は正確、普段は不要な数値やメタ的な消費説明を話さない |
| A15 | スマホ・PC、日英の会話、再接続 | 操作・音声・訂正・状態が整合し、導入や確定行動を重複しない |

状態遷移・競合・情報境界の自動テストと、実モデルの判断精度、実Liveの音声・テンポ、実機操作を分けて記録する。自然さ・柔軟性は具体例と失敗例を記録し、模擬テストで実音声が成功したと扱わない。マルチレビューはユーザー指示があるまで行わない。

## 9. 計画で解決する事項

- Liveの発話状態取得、警告の予約・置換・期限・優先順位、接続復旧時の扱い。実現できない制御が判明したら制約を明示する。
- 写真起点の判断とLive委譲の連携、道具を使わない観察の表現、行動の同一性と結果確定点、訂正と確定の競合制御。
- 許容方針・既知情報・開示条件・推測のスキーマと既存シナリオの移行。Live以外の会話出力経路にも同じ情報境界を適用する方法。
- 再試行の対象・期限・上流を含む上限、継続中/復旧不可の通知、モデル利用量への影響。
- 警告の初期秒数と待機上限、評価ケース、開発時に判断の短い理由を追う手段。生の写真・会話や秘密を本番ログに出さない。

本書はAPIの実現性、コードレビュー、動作検証の成功を示すものではない。
